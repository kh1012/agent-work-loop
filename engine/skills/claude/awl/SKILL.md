# awl — 얇은 오케스트레이션 스킬

지시는 CLI 가 만든다. 이 스킬은 세 줄이면 된다(adk-prototype.md:330-332).

1. 목표를 받으면 `awl next` 를 호출한다.
2. 출력에 다음에 할 일과 그 방법이 있다. 그대로 따른다. `skill` 줄이 채워져 있으면
   그 파일을 읽는다. 비어 있으면(`skill (없음)`) 계약만 보고 알아서 한다.
3. 끝나면 `awl record`(finding/clarification/attempt 등, 상황에 맞는 타입)로 결과를
   남기고 다시 `awl next` 를 부른다.

**게이트는 사람이 멈추는 자리다.** `awl next` 출력의 "게이트 N 에 도달하려면" 목록이
채워졌으면, 그 게이트에 해당하는 `awl record gate --json '{...}'` 를 기록하기 전에
`state.json` 의 **`loopMode`**(strict/semi-auto/auto, `awl state get`, 아무것도 안 주면
semi-auto)를 확인한다(adk-prototype.md:357-366):

> ⚠ **`mode` 가 아니라 `loopMode` 다.** `state.json` 의 `mode` 는 파이프라인 게이트-밀도
> (`gate-high`/`gate-medium`/`gate-low`)가 이미 쓰고 있어서 이름을 나눴다.
> `mode` 를 읽으면 레인에 따라 `gate-low` 같은 값이 나와 루프 모드로 오독된다.

```
strict      네 게이트에서 다 멈춘다 — 매번 AskUserQuestion 으로 승인을 받는다.
semi-auto   게이트 2·3 은 승인을 묻지 않고 "auto":true 로 자동 승인한다.
            게이트 1·4 는 그대로 묻는다(기본값).
auto        네 게이트 전부 자동 승인한다. 게이트 4(요청 닫기)만 완료 티켓·조건·
            검증·자동승인 횟수를 펼쳐 요약으로 보여준다(사람이 나중에라도 볼 수 있게
            — 승인을 묻지는 않는다).
```

**단계를 하나씩 지시받지 않는다.** 조사부터 하든 코드를 먼저 읽든 사람에게 먼저
묻든 상관없다 — 게이트에 도달할 때 `awl next` 가 요구한 형식(finding/clarification/
verification, 또는 커밋)만 맞으면 된다.

## 게이트 1 앞 — 캐묻기

스펙을 쓰기 전에 `awl next` 출력의 **모드** 절을 본다. 거기 "캐묻기(게이트 1 앞)" 줄이
지금 모드가 요구하는 강도를 그대로 말해준다.

```
strict      미해결 질문이 0건이 될 때까지 캐묻는다. 남은 게 있으면 게이트 1로 가지 않는다
semi-auto   한 번 캐묻고, 남은 것은 clarification 으로 기록한 뒤 진행한다
auto        건너뛴다 — 사람 손을 빼는 모드에서 캐묻는 건 모순이다
```

캐묻는 방법은 `profile.json` 의 `spec`·`clarification` 자리가 가리키는 스킬을 따른다
(기본은 grill-with-docs·grill-me). 읽을 수 없으면 그 스킬 없이 진행한다 — 무엇을 묻는지가
중요하지 어느 스킬로 묻는지가 중요한 게 아니다.

**캐묻기는 요청을 왜곡할 수 있다.** 파고들다 보면 원래 의도와 다른 방향으로 갈 수 있으니,
`Request` 절의 사용자 원문은 절대 고치지 않는다. 캐물어 정한 것은 `Instruction` 과
`Conditions` 로 간다.

## 게이트 4 — 마감 설명

요청을 닫을 때 사람에게 무엇을 남길지도 모드가 정한다.

```
strict      무엇을 왜 바꿨는지 사람이 읽을 형태로 남긴다. 이해를 확인하는 질문까지
semi-auto   무엇을 왜 바꿨는지 사람이 읽을 형태로 남긴다
auto        펼친 요약만 — 완료 티켓·조건·검증·자동승인 횟수
```

`profile.json` 의 `close` 자리가 그 형식을 가리킨다(기본은 explain-diff — 배경·직관·코드·
확인질문 네 절). **이건 리뷰가 아니다.** 리뷰는 다른 눈으로 결함을 찾는 자리(`review` 슬롯)고,
여기는 사람이 "에이전트가 무얼 했나"를 따라잡는 자리다. 자율로 오래 돌수록 이 부채가 커진다.

**티켓이 없으면 `awl next` 가 스펙 단계 뷰를 낸다.** 실패가 아니다 — 그 화면의
"다음" 절이 지금 할 수 있는 일을 실제 id 까지 넣어 알려주니 그대로 따르면 된다.
목표를 스펙으로 옮기는 순서는 이렇다: `awl doc new spec <제목> --request "<원문>"` →
`## Conditions` 를 `### condition-N` 블록으로 채우기(EARS 문형) → `awl tickets derive
<spec-id>` → 다시 `awl next`.

> 조건을 불릿(`- 언제 …`)으로 쓰면 `awl doc lint` 는 통과하는데 `awl tickets derive`
> 가 0개를 만들고 끝난다. 조건 하나가 `### condition-N` 소제목 하나다.

**문서(스펙·티켓)를 만들거나 고치면 그 자리에서 바로 커밋한다** — `git add
docs/ && git commit -m "..."` (`awl commit`이 아니라 그냥 git — 완료조건 diff
격리 대상이 아니라 문서라서 그렇다). 미루면 안 된다: `awl commit <ticket-id>
--start`는 그 시점 워킹트리의 미커밋 변경을 전부 "남의 것"으로 스냅샷해두므로,
그 전에 커밋 안 한 스펙/티켓 파일은 그 뒤로 어떤 티켓을 커밋해도 영원히 섞여
안 들어간다(시뮬레이션 발견, 2026-07-29).

**전체 파이프라인이 궁금하면** `awl stages`(전부) 또는 `awl stages --short`(다섯
줄)를 본다 — 이 스킬 파일이 다시 설명하지 않는다.

## 정성 검증과 반증 요구 (`--review`)

기본은 자가 검증이다. 서브에이전트를 안 띄운다. **다만 편향이 문제되는 판단에는
띄운다** — 만든 모델이 자기 산출물을 판정하면 의미가 없기 때문이다(설계 §10:1639-1642).

`--review` 가 켜져 있거나(`awl state get` 의 `review`) 스펙에 `## Qualitative` 루브릭이
있으면, 요청을 닫기 전에 **맥락을 모르는 세션 하나**를 띄워 판정을 받는다.

```
교차 모델        판정자를 다른 벤더로. 호스트는 파트너 출력을 안 보고 독립 분석
적대적 페르소나   각각 최소 하나는 반드시 찾게. 통과로 빠져나갈 수 없게
패널 토론        여러 리뷰어가 토론하고 최종 판정자가 결론
```

부존재도 여기서 본다 — "이 변경을 통째로 지우면 무엇이 깨지나."

**루브릭은 yes/no 로 묻는다.** 점수를 매기게 하면 대부분 4점이 나오고 4점이 무슨
뜻인지 아무도 모른다. no 가 나오면 구체적 지적이 따라온다.

티켓 레벨에서도 아래 중 **하나라도** 걸리면 그 자리에서 돈다(§10:1657-1665).

```
되돌리기 어렵다 (그 티켓에서 decision 이 나왔다)
기계 판정 비율이 낮다
전부 1차 통과에 막힘 0 (너무 쉬웠다는 신호)
이 영역에 gotcha 가 쌓여 있다
변경 범위가 크다
```

**전부 1차 통과에 막힘 0 은 축하할 일이 아니라 의심할 일이다.**
