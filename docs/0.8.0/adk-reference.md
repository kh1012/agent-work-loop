# 에이전틱 개발체계 — 형식 레퍼런스

`adk-interim.md` 가 왜와 무엇을 다룬다면, 이 문서는 실제 형식을 다룬다.
발표에는 안 쓰고 백데이터로 둔다.

---

## 산출물

| 파일 | 무엇 | 누가 읽나 |
|---|---|---|
| `adk-interim.md` | 왜 필요하고 무엇이 달라지는지 | 팀 리더 |
| `adk-reference.md` | 이 문서. 실제 형식과 그렇게 정한 이유 | 만드는 사람 |
| `deck/` | 발표자료 35장 (HTML, 장별 파일) | 발표 청중 |
| `adk-prototype.md` | 기존 awl 에 얹는 5단계 작업 계획 | 구현하는 사람 |

**이 문서는 결정과 그 근거를 담는다.**
형식만 적어두면 나중에 “이거 왜 이렇게 했지” 하면서 되돌리게 된다.

구현 순서는 맨 끝 **17장**에 있다.

### 이름이 둘이다

```
ADK    에이전틱 개발체계          방법론. 다르게 구현해도 된다
awl    @midasit-dev/awl · awl    그 방법론을 구현한 도구
```

**섞어 쓰지 않는다.** 단계와 게이트와 형식을 말할 때는 ADK 이고,
명령과 파일과 설정을 말할 때는 awl 이다.

이름을 나누는 이유는 도구를 갈아엎어도 체계가 안 흔들리게 하기 위해서다.
스크럼과 Jira 가 이름이 다른 것과 같다.

## 0. 원칙

### 계약과 절차를 나눈다

이 체계가 정하는 것에 두 가지가 섞여 있다.

```
계약    무엇이 나와야 하는가        사람과 조직이 쓴다
절차    어떤 순서로 어떻게 하는가    모델이 못 하니까 시킨 것
```

**가르는 기준은 누가 쓰느냐다.**

```
남는다    스펙 형식 · EARS · finding 의 file:line
          게이트 위치 · author · domain · terms
          → 사람이 읽고 중앙에서 검색한다. 모델이 좋아져도 그대로다

사라진다  investigation → clarification → spike 순서
          "코드를 읽으면 답이 나오면 묻지 마라"
          grill 규칙 · 단계별 스킬
          → 모델이 알아서 하면 필요 없다
```

모델이 아무리 좋아져도 스펙은 사람이 읽는다.
반면 조사를 어떤 순서로 하는지는 모델의 일이다.

### 계약 기반이면 무시당해도 안 무너진다

```
절차 기반    "이 순서로 해라"       모델이 다른 순서로 하면 어긋난다
계약 기반    "이게 나와야 한다"      어떻게 만들든 상관없다
```

모델이 우리 절차를 무시하고 한 방에 스펙을 써도 형식이 맞으면 통과다.
**단단한 하네스일수록 모델이 좋아질 때 더 크게 무너진다.**
계약만 남기면 무너질 것이 없다.

### 절차는 대부분 계약으로 번역된다

| 절차 | 계약 |
|---|---|
| 먼저 코드를 읽어라 | `finding` 이 비어 있으면 안 된다 |
| 모르는 건 사람에게 물어라 | `clarification` 이 목록이거나 `없음` 이어야 한다 |
| 모르는 건 코드로 확인해라 | spike 결과도 `finding` 에 `source` 로 남아야 한다 |
| 끝을 먼저 정의해라 | `verification` 이 given/when/then 이어야 한다 |
| 조건 하나에 티켓 하나 | 티켓의 `conditions` 가 1개 이하 |

**강제력은 그대로인데 방법이 자유로워진다.**
그리고 모델이 좋아져서 코드를 안 읽고도 알면 통과한다.
절차 쪽은 "읽었나"를 보는데 계약 쪽은 "아나"를 본다.

### 게이트가 순서의 골격이다

```
[gate 1] ─ 자유 ─ [gate 2] ─ 자유 ─ [gate 3] ─ 자유 ─ [gate 4]
```

**무질서가 아니다.** 게이트에 도달할 때 계약이 만족돼 있으면 되고
거기까지 어떻게 갔는지는 안 따진다.

게이트는 다른 축이다. 모델 능력이 아니라 **사람의 신뢰와 조직의 책임**에 대한 것이다.
모델이 완벽해도 사람이 "이거 맞나" 보고 싶으면 게이트가 필요하고,
누가 승인했는지가 남아야 한다.
그래서 게이트는 자리가 남고 **빈도만 줄어든다.**

### 안전망은 절차가 아니다

```
계약 검사    finding 이 비었나. verification 형식이 맞나
기계 검증    typecheck · test · e2e
리뷰         놓친 것. 부정행위
게이트       사람이 본다
```

넷 다 절차와 무관하다.
**절차의 원래 역할은 모델이 덤벙대지 않게 하는 것**이었고,
그건 모델이 좋아지면 없어도 된다.

### 언제 덜어낼지 잰다

지금 당장 절차를 다 빼자는 게 아니다. 지금 모델은 아직 필요할 수 있다.
다만 **계약에 박아두면 못 빼고 스킬에 두면 뺄 수 있다.**

```
지금          절차를 스킬로 둔다. 프로파일이 지정한다
모델 업데이트   스킬을 비우고 돌려서 결과를 비교한다
같으면         비운다
```

토큰 집계가 있으므로 비교할 재료도 있다.
스킬을 뺐을 때 토큰이 줄고 결과가 같으면 명백하다.
**감으로 덜어내지 않게 된다.**

## 0.1 이름 규칙

### 축약어를 쓰지 않는다

우리가 만든 것은 전부 풀 단어로 쓴다.
`AC`, `CN`, `FL` 같은 축약은 보여줬을 때 한 번에 안 읽혀서 버렸다.

```
condition-1     조건
constraint-1    제약
finding-1       조사에서 발견한 것
ticket-1        티켓
decision-1      되돌리기 어려운 결정
```

`e2e`, `JSON`, `UUID`, `git` 은 그대로 둔다. 우리가 만든 축약이 아니다.

### 저장과 표시가 같다

식별자는 파일에도 영문, 화면에도 영문이다. 한글 표시 계층을 두지 않는다.
매핑표가 없으니 어긋날 일이 없다. **산문 내용만 한글이다.**

### 검증 방법

새 이름을 정할 때는 다른 사람에게 보여주고 무슨 뜻일 것 같냐고 묻는다.
한 번에 안 나오면 바꾼다.

### 구조를 이름에 박지 않는다

`semi-gate` 는 게이트가 넷일 때만 맞는 말이다. 구조가 바뀌면 이름이 거짓말이 된다.
이름은 하는 일을 말해야지 구조를 참조하면 안 된다.

### config 이지 settings 가 아니다

```
settings   취향으로 바꾸는 것. 없어도 기본값으로 돈다
           VS Code · Claude Code · 브라우저 설정

config     없으면 안 도는 구조값
           tsconfig.json · webpack.config.js · .circleci/config.yml
```

우리 값은 `repository` 나 검증 명령처럼 **없으면 단계가 못 도는 것**이 대부분이다.
그리고 팀 전체가 쓰는 값인데 `settings` 라고 하면 개인 취향처럼 읽힌다.

`.claude/settings.json` 이 그 이름인 건 permissions 나 hooks 처럼
개인이 켜고 끄는 게 많아서다. 나란히 놓였을 때 이름이 다른 편이 헷갈리지 않는다.

### 디렉토리 안에서는 접두어를 안 붙인다

```
루트에 있으면      파일명이 스스로를 설명해야 한다
                  package.json · tsconfig.json · vite.config.ts

디렉토리 안이면    디렉토리가 설명한다
                  .circleci/config.yml · .vscode/settings.json
```

`.awl/` 이 이미 네임스페이스라 `package-config.json` 같은 접두어는 중복이다.

`package-` 는 모노레포에서 **틀린 말이 된다.** 저장소 하나에 패키지가 열 개인데
config 는 하나다. 패키지의 설정이 아니라 저장소의 설정이다.

`project-` 는 용어집에 이미 적어둔 Bitbucket 의 project 와의 혼동을 되살린다.

## 1. 디렉토리

### 세 층

```
~/.awl/
  config.json             전역 기본값               사람마다 한 번

  gotchas/                겪은 함정                 사람마다 쌓인다
  rules/active/           승격된 규칙                사람마다 쌓인다
  generations/<project>/  워크아이템 세대 지표        사람마다 쌓인다
  templates/              개인 초안 기본값

<repo>/
  .awl/
    config.json           이 저장소가 정한 것        커밋
    profile.json          이 저장소가 정한 것        커밋

    config.local.json     내 환경으로 덮는 것        untracked
    profile.local.json    내 환경으로 덮는 것        untracked

    state.json            지금 상태                 untracked
    .cache/               버려도 되는 것            untracked

  docs/
    CONTEXT.md                              용어집
    specs/20260725-143052-editor-keyboard-nav.md       스펙
    tickets/20260725-151203-keyboard-event-wiring.md   티켓
    decisions/20260725-160841-event-at-panel-root.md   결정
```

**학습은 사람 층에 둔다.** 위 네 칸(`gotchas` · `rules` · `generations` · `templates`)이
그 자리다. 프로젝트를 옮겨도 따라와야 "다음 프로젝트에서 빈손으로 시작하지 않는다"가
성립한다. 저장소에 두면 저장소를 나가는 순간 사라진다.

**기록(`records`)만 예외로 프로젝트 층이다**(`<repo>/.awl/records/`). 기록은 커밋·티켓과
1:1로 붙고 양이 크며, 레인이 여럿일 때 주 워킹카피 하나를 심링크로 가리켜 실시간 공유한다
(§14). 사람 층에 두면 레인마다 갈라져 정리 때 병합해야 하는데, 그건 §14 가 피하려는 바로
그 구조다.

**빌려온 관례가 셋이다.**

| 무엇 | 어디서 |
|---|---|
| `.local` 접미 = 덮어쓰기, 절대 커밋 안 함 | dotenv · Vite · Next.js 의 `.env.local` |
| 점 디렉토리 = 도구가 만들고 버려도 됨 | `.next/` · `.terraform/` · `.pytest_cache/` |
| 귀한 건 위, 버릴 건 아래 | npm · Cargo · Terraform 공통 |

npm 은 `package-lock.json` 이 위에 있고 `node_modules/` 가 아래다.
Cargo 는 `Cargo.lock` 이 위고 `target/` 이 아래다.
Terraform 은 `terraform.tfstate` 가 위고 `.terraform/` 이 아래다.

**지우면 아픈 건 최상위에, `rm -rf` 해도 되는 것만 점 디렉토리에.**

`.cache/` 는 지금 비어 있어도 된다. **이름만으로 "여긴 지워도 된다"가 전달되는 게 값어치다.**

### gitignore 는 허용목록으로

```gitignore
.awl/*
!.awl/config.json
!.awl/profile.json
```

**두 줄이고, 새 파일이 생겨도 기본이 untracked 다.**
나중에 뭘 추가하다가 개인 메일이나 토큰이 딸려 올라가는 사고가 구조적으로 안 난다.

거부 목록으로 쓰면 파일이 늘 때마다 한 줄씩 추가해야 하고, 빠뜨리는 순간 유출된다.

### `.claude/` 와 같은 모양이다

```
~/.claude/settings.json           ~/.awl/config.json          전역 기본값
.claude/settings.json             .awl/config.json            프로젝트
.claude/settings.local.json       .awl/config.local.json      개인
.claude/skills/ commands/         docs/ 는 저장소 루트
```

**엔진은 전역이고 프로젝트에는 설정만 둔다.**
`npm i -g` 하나로 업데이트되고, 저장소에는 버전이 안 박힌다.

이 구조를 따르면 설명이 한 줄로 끝난다.
"`~/.claude` 에 한 번 설정하고 프로젝트마다 `.claude` 두는 것과 같습니다."

### 엔진 사본을 두지 않는다

이전 설계는 `~/.awl/engine/` 에 엔진을 한 벌 더 복사했다.
그래서 어긋날 수 있는 버전 짝이 넷이 됐고, 그걸 감지하는 장치를 따로 만들어야 했다.

```
사라진 것
  ~/.awl/engine/        사본
  awl update            npm i -g 로 끝난다
  engineVersion         저장소에 버전을 안 박는다
  버전 불일치 감지       짝이 하나뿐이라 어긋날 게 없다
```

**npm 패키지가 유일한 엔진이다.** LLM 을 전역으로 맞추듯 도구도 전역으로 맞춘다.

스키마가 바뀌면 관용적으로 읽는다. 모르는 키는 무시하고 없는 키는 기본값을 쓴다.
깨는 변경이 실제로 생길 때만 버전 필드를 도입한다.

### 파일명

```
[YYYYMMDD]-[HHMMSS]-[kebab-제목].md
```

```
docs/specs/20260725-143052-editor-keyboard-nav.md
docs/tickets/20260725-151203-keyboard-event-wiring.md
docs/decisions/20260725-160841-event-at-panel-root.md
```

**순번을 안 쓰는 이유**

분산 저장소에서 순번은 안 맞는다.

```
A 가 브랜치를 판다    디렉토리를 훑어 max+1 = 00042
B 가 브랜치를 판다    똑같이 00042
둘 다 머지된다        파일명이 다르므로 git 이 충돌을 안 낸다
```

**조용히 통과한다.** 그게 최악이다. 시끄럽게 터지면 고치면 되는데 안 터진다.

중앙에서 번호를 발급하면 풀리지만 중앙이 죽으면 문서를 못 만들게 된다.
로컬 우선 원칙과 정면으로 부딪힌다.

Rails 가 같은 길을 갔다. 처음엔 `001_create_users.rb` 였는데
팀 작업에서 충돌이 계속 나서 2.0 에서 타임스탬프로 바꿨고 다른 도구들도 따라갔다.
**각자 브랜치에서 파일을 만들고 나중에 합치고 순서가 의미를 갖는다**는 조건이 우리와 같다.

**날짜만으로 부족한 이유**

같은 날 만든 것들의 순서가 안 보인다.

```
날짜만    20260725-editor-keyboard-nav.md
          20260725-layer-panel-focus.md
          20260725-toolbar-shortcut.md          제목순으로 섞인다

초까지    20260725-091214-toolbar-shortcut.md
          20260725-143052-editor-keyboard-nav.md
          20260725-171840-layer-panel-focus.md  만든 순서대로
```

활발한 프로젝트면 하루에 티켓 서너 개가 나온다. 그때 순서가 보이는 게 실제로 편하다.

**하이픈 위치**

```
2026-07-25-143052-editor-keyboard-nav.md      어디까지가 시각인지 흐리다
20260725-143052-editor-keyboard-nav.md        두 덩어리라 명확하다
```

앞의 것은 하이픈으로 쪼개면 날짜가 세 조각이라
**제목 구분자와 날짜 구분자가 같아서 경계가 안 보인다.**

**시각은 로컬로 쓴다**

```
파일명        20260725-143052-...                  로컬 시각. 사람이 본다
프론트매터    created: 2026-07-25T14:30:52+09:00   정확한 값
```

Rails 가 UTC 를 쓰는 건 팀이 시간대를 넘나들기 때문이다.
사내 도구면 로컬이 읽기 좋고 정확한 값은 프론트매터가 갖는다.

**참조는 여전히 UUID 다.** 파일명은 디렉토리에서 눈으로 찾는 용도이고 링크는 안 깨진다.

### 하위 디렉토리를 만들지 않는다

`specs/active/`, `specs/closed/` 로 나누면 상태가 바뀔 때마다 파일을 옮겨야 하고
git 히스토리가 지저분해진다. **상태는 프론트매터에 둔다.**

## 2. 스펙

### 프론트매터

```yaml
id:            0192f8a1-7c3d-7e4a-b2f1-9d8e6c4a1b03
revision:      sha256:a3f9c2...
organization:  platform-lab
project:       maxflow
title:         레이어 패널 키보드 조작
status:        active
domain:        editor
terms:         [레이어, 티켓]
verification:  [binary, qualitative]
tickets:       [ticket-1, ticket-2, ticket-3]
decisions:     [decision-1]
created:       2026-07-23
updated:       2026-07-23
```

**가르는 기준**: 본문을 안 열고 "이게 내가 찾던 것인가"를 판단할 수 있는 최소한.

| 필드 | 왜 프론트매터인가 |
|---|---|
| `id` | UUIDv7. 안 바뀐다. 참조용 |
| `revision` | 내용 해시. 바뀐다. 전송 멱등성용 |
| `organization` | 소유 팀. 경로에는 안 쓴다 |
| `terms` | **부서 간 검색의 실제 열쇠** |
| `verification` | 정량·정성 레이어를 붙일지. 스펙 단계에서 판정 |
| `decisions` | 결정은 별도 파일이라 링크로 연결 |

`id` 는 스펙이 수정돼도 안 바뀐다. 내용 해시를 id 로 쓰면 고칠 때마다 링크가 끊긴다.

### status

```
draft    grill 중. 아직 티켓 안 나옴
active   게이트 1 통과. 티켓이 돌고 있음
closed   게이트 4 통과
```

**게이트 통과가 곧 상태 전이다.** 사람이 손으로 고치는 게 아니다.

일시정지는 상태가 아니라 별도 필드다.

```yaml
status:    active
paused:    true
resumeAt:  2026-07-25T15:00:00Z
```

직교하는 성질이라 따로 둔다. 풀 때 원래 자리로 그냥 돌아간다.

### 본문

```markdown
## Request
> 레이어 패널 키보드로 조작하고 싶어
> 방향키로 움직이고 엔터로 선택되면 좋겠어

## Instruction
레이어 패널을 키보드만으로 다룰 수 있게 한다.
마우스를 쓸 수 없는 상황에서도 편집이 가능해야 한다.

## Constraints

### constraint-1
Puck 코어를 수정하지 않는다

verification: git diff 에 @measured/puck 없음
source: -
hits: 0

### constraint-2
e2e 는 포트를 격리한 뒤 실행한다

verification: 테스트 시작 시 lsof 로 점유 프로세스 확인
source: gotcha-014
hits: 2

## Conditions

### condition-1
언제 포커스가 패널에 있고 위·아래 방향키를 누르면,
선택이 한 칸씩 이동해야 한다

### condition-2
언제 노드에 자식이 있고 좌·우 방향키를 누르면,
접히거나 펼쳐져야 한다

### condition-3
만약 이름 편집 중이라면,
방향키는 선택을 이동시키지 않아야 한다

## Qualitative
- 키보드만으로 패널의 모든 노드에 도달할 수 있는가
- 지금 어느 노드가 선택됐는지 시각적으로 알 수 있는가

## Out of scope
- 다중 선택       ItemSelector 가 단일값. 큰 작업
- 드래그 재정렬    이번 요청과 무관
```

### Request 를 남기는 이유

grill 이 요청을 왜곡할 수 있다. 캐묻다 보면 원래 의도와 다른 방향으로 갈 수 있는데,
그러면 스펙은 정교한데 엉뚱한 걸 만든다. **원문이 있어야 커버리지 판정의 기준이 선다.**

프론트매터가 아닌 이유는 `title` 이 이미 목록 조회 역할을 하고, 원문이 여러 줄일 수 있어서다.

### 세 가지를 담는다

| | 무엇 |
|---|---|
| Instruction | 무엇을 왜 만드나 |
| Constraints | 무엇은 건드리면 안 되나 |
| Conditions | 무엇이 되면 끝인가 |

**Constraints 를 빠뜨리기 쉽다.**
"안 만드는 것"(Out of scope)과 "건드리면 안 되는 것"(Constraints)은 다르다.

**정지 조건 항목은 없다.** Conditions 의 합이 곧 정지 조건이라 중복이다.

### 스펙에 파일 경로를 쓰지 않는다

금방 낡는다. 경로는 finding 에만 쓴다. finding 은 티켓 수명이라 괜찮다.

## 3. EARS

조건은 다섯 문형으로만 쓴다.

```
언제      <조건>이면, 시스템은 <동작>해야 한다
만약      <예외>라면, 시스템은 <동작>해야 한다
동안      <상태>인 동안, 시스템은 <동작>해야 한다
어디서    <기능>이 켜져 있으면, 시스템은 <동작>해야 한다
항상      시스템은 <동작>해야 한다
```

**조건과 동작이 분리된다.** 그래서 검증이 번역으로 나온다. 창작이 아니다.

**모순이 잡힌다.** 같은 조건에 다른 동작을 요구하면 기계가 찾는다.

**빠뜨린 예외가 보인다.** "언제"만 있고 "만약"이 하나도 없으면 예외를 안 생각한 것이다.

---

## 4. 티켓

### 프론트매터

```yaml
id:           0192f8b2-...
spec:         0192f8a1-...
conditions:   [condition-1]
dependencies: [ticket-1]
status:       implementing
```

`conditions` 가 비어 있을 수 있다.
여러 조건이 공유하는 기반을 만드는 티켓이다. 사용자가 관찰할 수 없어 조건이 될 수 없다.

### status

```
pending        아직 시작 안 함
implementing   구현 중
reviewing      리뷰 중
done           완료
blocked        3회 실패로 막힘
```

`paused` 와 `resumeAt` 은 스펙과 같다. 상태가 아니라 별도 필드다.

### 본문

```markdown
## Verification
given  레이어 패널에 포커스가 있다
when   아래 방향키를 누른다
then   aria-selected 가 다음 행으로 이동한다

타입: e2e

## Clarifications
- 이름 편집 중에는 방향키가 선택을 안 옮긴다
- 맨 아래에서 아래키는 순환하지 않는다

## Files
LayersPanel.tsx, keyboard.tsx
```

**Verification 도 EARS 구조를 따른다.** 조건의 `언제 X 이면 Y` 에서
X 가 given·when 으로, Y 가 then 으로 간다. 번역이지 창작이 아니다.

### 조건을 복사하지 않는다

티켓은 `conditions` 로 가리키기만 한다.
복사하면 스펙이 수정됐을 때 갈라지고, 둘 중 뭐가 맞는지 아무도 모른다.

**보여줄 때는 도구가 조립한다.** 저장은 참조, 표시는 조립.

### 분해 규칙

```
조건 하나              → 티켓 하나 (기본)
여러 조건이 공유하는 기반 → 별도 티켓 (conditions 비어 있음)
한 조건 안의 순차성     → 커밋으로 표현
```

**의존이 곧 구현 순서다.** 순서를 따로 정하지 않는다.

```
ticket-1  키보드 이벤트 배선    conditions: []
ticket-2  선택 인덱스 유틸      conditions: []
ticket-3  방향키 이동           conditions: [condition-1]
ticket-4  접기·펼치기           conditions: [condition-2]

의존  ticket-3, ticket-4 ← ticket-2 ← ticket-1
```

`conditions` 가 빈 티켓이 필요한지는 AI 가 판정한다. 사람은 개수만 본다.

### 완료돼도 지우지 않는다

`status` 만 바꾼다. 완료 조건이 그 파일에 있어서, 지우면 나중에 git 히스토리를 파야 한다.

---

## 5. 결정

`docs/decisions/` 에 둔다. **되돌리기 어려운 것만.**

모든 결정을 남기면 아무도 안 읽는다.

```yaml
id:            0192f8c3-...
status:        accepted
supersedes:    -
superseded-by: -
```

```
accepted     유효하다
superseded   다른 결정으로 대체됐다      superseded-by 링크가 있다
deprecated   더 이상 유효하지 않은데 대체 결정이 없다
```

셋 다 ADR 표준 용어다. `proposed` 는 안 쓴다.
결정이 내려질 때 쓰지 논의 중에 쓰는 게 아니다.

**결정은 수정하지 않는다.** 바뀌면 새 결정을 써서 이전 것을 supersede 한다.

### clarification 과의 관계

```
clarification    전부 티켓에 쌓는다
decision         그중 되돌리기 어려운 것만
안 남김          단순 확인 (판단이 없었던 것)
```

판정은 AI 가 한다. 사람은 안 본다.

**같은 clarification 이 3회 반복되면 승격 후보 신호가 뜬다.**
"되돌리기 어렵다"는 미리 알기 어렵지만, 반복은 사후에 확실하다.

## 6. 용어집

`docs/CONTEXT.md` 에 둔다. 표가 아니라 섹션 형식이다.

```markdown
## 티켓
스펙에서 도출된, 독립적으로 검증 가능한 작업 단위.

- 쓰지 않음: 태스크, 이슈, 일감
- 코드: `Ticket`, `ticketId`

## 프로젝트
프로파일이 붙는 단위. 저장소 하나에 대응한다.

- 쓰지 않음: -
- 주의: Bitbucket Server 의 project 와 다른 것을 가리킨다
```

### 왜 섹션인가

AI 는 파일을 통째로 읽으니 형식이 무관하다.
**문제는 검사기다.** 마크다운 표에서 세 번째 열만 파싱하는 건 취약하다.

`- 쓰지 않음:` 이 고정 접두어라 한 줄 정규식으로 잡힌다.
정의가 길어지거나 예시가 붙어도 안 깨진다.

**"쓰지 않음"이 제일 쓸모 있다.** grep 으로 바로 검사된다.

## 7. 설정 파일

### 무엇이 어디로 가나

```
~/.awl/config.json      전역       author · sync            사람마다 한 번

.awl/config.json        커밋       이 저장소의 사실
.awl/profile.json       커밋       각 단계를 어떤 방식으로
.awl/config.local.json  untracked  내 머신 차이
.awl/profile.local.json untracked  내 방식
.awl/state.json         untracked  진행 상태와 모드
.awl/.cache/            untracked  버려도 되는 것
```

**세 축이 겹쳐 있다.**

```
어느 층이냐     전역 → 저장소 → 개인. 아래가 위를 덮는다
공유되나        profile 은 남에게 줄 수 있고 config 는 이 저장소 것이다
무엇을 담나     config 는 사실, profile 은 선택
```

**커밋되는 파일에 비밀이 없다.** 토큰과 신원은 전역에 있다.

### 검증은 config 에만 둔다

한때 프로파일에 목록을 두고 config 에 명령을 두어 나눴다. 되돌렸다.

```
{ "name": "typecheck" }     담긴 정보가 없다
                            어떤 검사가 있는지는 자기 프로젝트를 보면 안다
```

**공유 가치가 갈린다.**

```
skills               남이 뭘 쓰는지 모른다        공유 가치 높다
verifications 목록    package.json 보면 안다      낮다
verifications 명령    프로젝트마다 다르다          없다
```

그리고 같은 이름이 두 파일에 있는 것이 혼란의 원인이었다.
**`verifications` 는 config 에만 있고 profile 은 스킬만 담는다.**

**검증 명령이 프로파일에 있으면 안 된다.**
남의 프로파일에 `vitest run` 이라고 적혀 있는데 우리는 jest 를 쓰면 그냥 틀린 값이다.
받아도 못 쓰는 값을 공유하는 셈이다.

### profile.json — 공유 가능

```json
{
  "name": "FE 출시 직전",
  "description": "grill 을 촘촘히 하고 리뷰에 교차 모델을 쓴다. 안정화 구간용.",

  "skills": {
    "spec":          { "type": "external", "url": ".../grill-with-docs" },
    "investigation": null,
    "clarification": { "type": "external", "url": ".../grill-me" },
    "spike":         null,
    "implement":     { "type": "custom",   "path": ".claude/skills/our-tdd" },
    "review":        { "type": "external", "url": ".../adversarial-review", "version": "0.3" }
  }
}
```

**JSON 인 이유**는 공유 공간에서 생성·업로드하고 JSON 으로 받아오기 때문이다.
형식 변환이 없다. 주석 대신 `note` 필드를 쓴다.
공유 공간 화면에 그대로 띄울 수 있어 오히려 낫다.

**프로파일에는 스킬만 있다.** 각 단계를 어떤 방식으로 할지의 선택이다.
검증은 이 저장소의 사실이라 `config.json` 에 있다.

**`stage` 를 두지 않는다.** `name` 과 중복이다.
`description` 이 훨씬 쓸모 있다. 고정된 값에서 고르는 게 아니라
"이걸 언제 쓰나"를 자유롭게 쓰고, 마켓플레이스에서 전문 검색으로 찾는다.

**`language` 를 두지 않는다.** 하는 일이 없다.
검증 명령이 이미 언어를 말하고, 없어도 단계가 돌아간다.

**생애주기 단계별 섹션도 두지 않는다.**
한 번에 한 단계에만 있는데 세 단계를 다 담을 이유가 없다.
출시 직전이 되면 그 시점 프로파일을 받아 갈아끼운다.

### config.json — 이 저장소 것

```json
{
  "repository": "midasit/maxflow",

  "verifications": [
    { "name": "typecheck", "cmd": "tsc --noEmit", "cwd": "packages/editor" },
    { "name": "lint",      "cmd": "biome check ." },
    { "name": "test",      "cmd": "vitest run" },
    { "name": "a11y",      "cmd": "pnpm axe", "scope": "changed" },
    { "name": "e2e",       "cmd": "playwright test", "level": "request",
      "note": "포트 격리 후 실행. gotcha-014" }
  ]
}
```

**둘뿐이다.** 이 저장소의 사실만 남았고 파생 상태는 전부 빠졌다.

**공유 프로파일을 받아도 이 파일은 안 덮어쓴다.**

`sync` 와 `author` 는 여기 없다. 전역으로 갔다.
저장소가 다른 중앙을 쓴다면 여기서 덮을 수 있지만 보통은 비어 있다.

**이름 규칙**: `url` 은 사람이 열어볼 수 있는 것(스킬 저장소),
`endpoint` 는 호출하는 API 진입점(sync).

`repository` 는 git remote 에서 유도한다. 중앙의 경로가 된다.
ssh 와 https 형식이 다르므로 정규화한다.

```
git@bitbucket.org:midasit/maxflow.git
https://user@bitbucket.org/midasit/maxflow.git
                    ↓
              midasit/maxflow
```

### 설치 목록을 두지 않는다

한때 `installedSkills` 로 무엇이 설치됐는지 기록했다. 뺐다.

**진실은 `.claude/skills/` 에 있고 그것은 사본이다.**
`~/.awl/engine/` 이 엔진의 사본이라 어긋났던 것과 같은 실수다.

```
url          profile.json 에 이미 있다
설치 여부     .claude/skills/<name>/ 이 있는지 보면 된다
version      스킬이 커밋되므로 git 이 안다
```

버전 추적은 두 곳이 더 낫다.

```
git      git log .claude/skills/  →  언제 뭐가 바뀌었나
기록      "이 티켓은 grill-me 1.1 로 했다"  →  중앙에서 집계된다
```

**기록 쪽이 특히 쓸모 있다.** 정적 목록과 달리
"이 스킬을 쓴 티켓들이 리뷰 지적이 적나" 같은 것을 볼 수 있다.

### 무엇을 적고 무엇을 안 적나

```
확인할 수 있는 사실     안 적는다     .claude/skills/ 를 보면 안다
고정하기로 한 결정      적는다        remote 가 바뀌어도 경로는 안 바뀐다
```

`repository` 가 후자다. remote 를 옮기거나 호스트를 이전하면 유도값이 바뀌는데,
그러면 중앙의 경로가 통째로 갈라진다. **박아두면 안 바뀐다.**

처음 한 번 remote 에서 유도하고 그다음은 파일이 진실이다.

`name` 이 아닌 이유는 셋이다. `config.json` 안에서 `name` 은 무엇의 이름인지 안 나오고,
`profile.json` 의 `name` 은 사람이 붙인 라벨이라 같은 키가 두 파일에서 다른 것을 가리키게 되고,
`midasit/maxflow` 는 이름이 아니라 **주소**다. `package.json` 의 `repository` 와 같은 자리다.

### verifications

**배열이다.** 순서가 의미를 갖기 때문이다.

```
typecheck  1초
lint       0.2초
test       7초
e2e        60초
```

싼 것부터 돌려서 빨리 실패해야 한다. 객체로 두면 순서가 계약이 아니라 우연이 된다.

이름은 자유롭게 확장한다. `a11y`, `perf`, `security` 를 넣어도 된다.

```
scope: all      (기본) 전체를 본다
scope: changed  변경한 파일에서 나온 실패만 본다

level: ticket   (기본) 티켓마다 돈다
level: request  요청을 닫을 때 한 번 돈다
```

**e2e 는 `level: request` 다.** 여러 조각을 가로지르는 검증이라
애초에 티켓 레벨이 아니었다. 티켓 5개면 290초가 58초가 되고
`exclusive` 충돌도 요청당 1회라 거의 안 부딪힌다.

이것이 검증 3층과도 맞는다. binary 는 티켓, 나머지는 요청인데
e2e 를 티켓에 둔 것이 예외였다.

새 검사를 추가하면 기존 코드에서 잔뜩 실패하는 게 보통이다.
`changed` 가 없으면 팀이 새 검사를 아예 안 넣는다. 넣는 순간 빨간불이니까.

베이스라인 대조를 안 쓰는 이유는, 린트는 위에 한 줄만 추가돼도
아래가 전부 밀려서 새 실패로 잡히기 때문이다.

### 정책은 프로파일이 아니라 시점에 알려준다

"새 검사는 `changed` 로 시작해라" 같은 것은 남의 경험이다.
프로파일에서 검증이 빠지면서 그것을 물려줄 자리도 사라졌다.

**필요한 순간에 나오게 한다.**

```
$ awl config add-verification a11y

  이 검사를 처음 넣습니까?
  기존 코드에서 실패가 많이 나올 수 있습니다.
  scope: changed 로 시작하면 이번 변경분만 봅니다.

  (*) changed 로 시작   ( ) all
```

**프로파일에 박아두는 것보다 낫다.** 필요할 때 나오고 왜 그런지도 설명된다.

### 부트스트랩

프로파일을 받으면 거기 적힌 스킬 중 설치 안 된 것을 받는다.
`url` 을 보고 `.claude/skills/` 에 넣는다.
**설치됐는지는 그 디렉토리가 있는지로 안다.** 따로 기록하지 않는다.

검증은 프로파일에 없으므로 물어볼 것이 없다. 이 저장소의 `config.json` 이 이미 갖고 있다.

### skills

**자리는 일곱이다. 파이프라인 순서로 쓴다.**

> 초안은 여섯이었다. 게이트 4의 마감 설명이 자리를 못 가져 `review` 를 빌려 쓰고 있었는데,
> 리뷰(다른 눈으로 편향 회피)와 마감 설명(사람의 인지 부채 감소)은 목적이 달라 둘 중 하나만
> 가질 수 있었다. `close` 를 일곱째로 뒀다(0.9.5).

```
spec           스펙을 만드는 방식
investigation  코드를 훑는 방식
clarification  남은 걸 묻는 방식
spike          모르는 걸 판정하는 방식
implement      구현 방식 (tdd 등)
review         반증 요구 방식
close          마감 설명 방식 (사람이 무엇이 바뀌었는지 따라잡는 자리)
```

`tickets` 는 도출이 기계적이라 갈아끼울 여지가 없고,
`verify` 는 스킬이 아니라 명령이라 `verifications` 에 이미 있다.

**자리당 하나만 둔다.** 배열로 두면 조합 규칙(순차·병렬·충돌 시 우선순위)을
프로파일이 정해야 하고, 그러면 프로파일이 프로그램이 된다.
여러 기법을 쓰려면 그걸 묶은 스킬을 만든다.

**스킬은 두 종류다.**

```json
{ "type": "external", "url": "https://github.com/mattpocock/skills/.../grill-me" }
{ "type": "custom",   "path": ".claude/skills/our-review" }
```

| type | 뜻 | 필수 | 설치 |
|---|---|---|---|
| `external` | 외부 저장소에서 받아온 것 | `url` | 받아서 넣는다 |
| `custom` | 이 저장소에 직접 쓴 것 | `path` | 이미 있다 |

`remote` / `local` 쌍이 더 대칭이지만 **`local` 이 `.local.json` 파일과 겹쳐서** 쓰지 않는다.
같은 문서 안에서 한 단어가 두 가지를 가리키면 안 된다.

**외부 스킬을 고쳐 쓰면 `custom` 이 되고 `basedOn` 으로 원본을 남긴다.**

```json
{
  "type": "custom",
  "path": ".claude/skills/our-grill",
  "basedOn": "https://github.com/mattpocock/skills/.../grill-me"
}
```

받아온 그대로가 아니므로 다시 받으면 안 되고, 원본이 어디였는지는 알아야 한다.
나중에 원본이 좋아지면 비교해서 다시 가져올지 판단할 수 있다.

**나머지는 선택이다.**

```
name      없으면 url 이나 스킬 파일에서 유도한다
install   설치 명령이 따로 있으면. 없으면 url 에서 받아 복사한다
version   특정 버전이 필요할 때만. 없으면 설치 시점 최신
```

**버전을 안 박아도 되는 이유**는 스킬이 `.claude/skills/` 에 커밋되기 때문이다.
첫 셋업하는 사람이 설치해 커밋하면 나머지는 클론만 하므로 전원이 같은 버전을 쓴다.
프로파일의 버전은 첫 설치 때만 쓰이고, 그 뒤로는 저장소 안의 파일이 진실이다.

추적은 git 과 기록이 맡는다.

**비어 있어도 돌아간다.** `null` 이면 에이전트가 계약만 보고 알아서 한다.
기본 스킬을 시스템에 박지 않는다. 추천은 공유 공간의 프로파일이라는 데이터로 준다.

### 스킬을 비워보는 것이 시험이다

스킬은 절차이고 절차는 모델이 좋아지면 사라진다.
**언제 사라졌는지를 재는 방법이 있다.**

```
스킬 있음    산출물이 계약을 만족한다
스킬 없음    산출물이 계약을 만족한다    →  그 절차는 이미 필요 없다
```

모델을 올릴 때마다 재본다. 결과가 같고 토큰이 줄면 비운다.
**하네스를 언제 걷을지가 측정 가능한 질문이 된다.**

### 오케스트레이션 스킬은 얇다

스킬이 두 종류다.

```
오케스트레이션 스킬    awl 자신. 얇다. 거의 안 바뀐다
단계 스킬              grill-with-docs 등. 프로파일이 지정한다. 갈아끼운다
```

`.claude/skills/` 에 설치되는 것은 사본이라 엔진이 올라가도 안 따라온다.
**그래서 오케스트레이션 스킬을 얇게 만들어 드리프트할 게 없게 한다.**

```markdown
# .claude/skills/awl/SKILL.md

목표를 받으면 `awl next` 를 호출한다.
출력에 다음에 할 일과 그 방법이 있다. 그대로 따른다.
끝나면 `awl record` 로 결과를 넘기고 다시 `awl next` 를 부른다.
```

지시는 CLI 가 만든다.

```
$ awl next

  ticket       ticket-4  접기·펼치기
  condition    condition-2
               언제 노드에 자식이 있고 좌·우 방향키를 누르면,
               접히거나 펼쳐져야 한다
  constraints  constraint-1, constraint-2   [전문]
  known        finding 6건                  [전문]
  skill        (없음)

  게이트 2 에 도달하려면
    finding        새로 알게 된 것. file:line 포함
    clarification  물어서 정한 것. 없으면 "없음"
    verification   given/when/then

  게이트 3 에 도달하려면
    커밋           검증이 통과하는 상태
```

**단계를 하나씩 지시하지 않고 계약을 통째로 준다.**
조사부터 하든 코드를 먼저 보든 사람에게 먼저 묻든 상관없다.
게이트에 도달할 때 위 형식이 나오면 된다.

`skill` 이 꽂혀 있으면 그 파일을 읽으라는 줄이 하나 붙는다.
비어 있으면 계약만 보고 알아서 한다.

**얻는 것 셋.**

```
전역 업데이트만으로 지시까지 최신이 된다
프로파일만 바꿔도 동작이 바뀐다. 스킬 파일은 안 건드린다
"awl 은 상태를 관리하고 에이전트가 판단한다"는 원칙에 더 맞는다
```

CLI 가 상태 기계를 돌리고 매 단계에서 무엇을 할지 알려주는 모양이다.

### awl stages

얇게 만들면 스킬 파일만 봐서는 파이프라인이 안 보인다. 명령으로 푼다.

```
$ awl stages

  요청 층
    spec          스펙을 만든다
      grill                          grill-with-docs
      glossary    용어집을 갱신한다    내장
    tickets       티켓을 만든다
      derive                         내장
      [gate 1]    이 티켓들로 요청이 만족되는가

    ... 티켓 층 반복 ...

    close         요청을 닫는다
      qualitative 정성 판정            adversarial-review
      [gate 4]    실제로 만족됐는가

  티켓 층                              티켓마다
    investigation 코드를 읽는다         (없음)
    clarification 남은 걸 묻는다        grill-me
    design        만들 것을 정한다      내장
    spike         모르는 걸 판정한다    (없음)
      [gate 2]    착수
    implement     만든다                tdd
    verify        기계가 판정한다        내장
    review        다른 눈이 본다        adversarial-review
      [gate 3]    완료
    record        남긴다                내장
```

**세 종류가 섞여 있다.**

```
갈아끼운다    프로파일이 스킬을 지정한다        grill · tdd · review
내장          기계적이라 갈아낄 게 없다         derive · verify · record
게이트        사람이 멈추는 자리                1 · 2 · 3 · 4
```

`(없음)` 은 스킬을 안 꽂은 자리다. 에이전트가 자기 방식으로 하고 품질만 달라진다.

**내장인 것들은 갈아낄 여지가 없어서 내장이다.**

```
derive     스펙에서 티켓을 뽑는 건 기계적이다. 조건 하나에 티켓 하나
verify     스킬이 아니라 명령이다. config 의 verifications 가 담당
record     형식이 고정이라 방식이 갈릴 게 없다
glossary   용어집 갱신은 규칙이지 판단이 아니다
```

**다섯 단계는 말할 때 쓰는 이름이다.**

```
말할 때      setup · spec · tickets · implement · verify
실행할 때    위의 두 층
```

`awl stages --short` 면 다섯 줄, 그냥 `awl stages` 면 전부 나온다.

### 계약은 파일로 둔다

`awl next` 가 매번 계약을 출력하면 같은 내용이 반복된다.
**정적인 것은 파일에 두고 한 번 읽게 한다.**

```
.awl/stages.md      단계의 계약. awl 이 생성. untracked. 항상 현재 버전
```

```markdown
# CLAUDE.md
...프로젝트 고유 내용...

@.awl/stages.md
```

CLAUDE.md 는 한 줄만 갖고 내용은 awl 이 만든다.
**커밋되는 파일에 계약을 박으면 awl 을 업데이트해도 안 따라온다.**
참조로 두면 항상 현재 버전이고, `awl doctor` 가 없거나 낡았으면 재생성한다.

참조가 안 되면 마커 사이를 갱신하는 방법도 있다.

```markdown
<!-- awl:stages:start -->
...awl 이 여기를 덮어쓴다...
<!-- awl:stages:end -->
```

**도구마다 읽는 파일이 다르다.** 원본 하나를 두고 각 파일이 가리키게 한다.

```
.awl/stages.md      원본. awl 이 생성
CLAUDE.md           참조
AGENTS.md           참조
```

### stages.md 에는 계약만 넣는다

```markdown
| 단계 | 입력 | 출력 | 끝났다는 판정 |
|---|---|---|---|
| investigation | 조건 · 기존 finding | finding 목록 + file:line | 조건을 건드리는 경로가 전부 목록에 있는가 |
| clarification | 코드 · 계획 | 정한 것 목록 또는 "없음" | 코드로 답할 수 있는 질문이 안 남았는가 |
| implement | 조건 · finding | 커밋 | 검증이 통과하는가 |
```

**설명은 스킬 파일이 갖는다.** 계약은 짧고 구현은 길다.

짧아야 하는 이유가 둘이다.
CLAUDE.md 는 모든 세션이 읽는데 리뷰어 서브에이전트는 단계 정의가 필요 없다.
그리고 **절차를 여기 적으면 모델이 좋아졌을 때 못 뺀다.**

### TDD 와 DDD 의 자리가 다르다

```
단계 안에서 실행되는 방식   → 스킬       (TDD)
프로젝트 전체 관례          → 용어집·규칙 (DDD)
```

DDD 의 유비쿼터스 언어가 곧 우리 용어집이고 바운디드 컨텍스트는 프로젝트 경계다.
프로파일 항목으로 만들 게 아니다.

### 마켓플레이스 등록

```
프로파일 등록

  ( ) 직접 입력
  ( ) 파일 업로드
  (*) URL 로 가져오기
      > https://bitbucket.org/midasit/maxflow
        .awl/profile.json 을 읽어옵니다.
```

**URL 방식이 가장 흔한 경우다.** 이미 잘 돌아가는 저장소를 가리키면 되니
입력할 게 하나고, 실제로 쓰이는 프로파일이라는 게 보장된다.
스킬 url 도 그 안에 들어 있어 따로 채울 게 없다.

업로드는 파일은 있는데 저장소를 공개 못 할 때, 직접 입력은 처음부터 새로 만들 때 쓴다.

### 로컬 오버라이드 — 커밋 안 함

`.local` 접미는 Next.js·Vite 관례라 설명이 필요 없다.

**가르는 원칙은 하나다.**

> 판정 기준은 팀이 같아야 하고, 만드는 방식은 개인이 골라도 된다.

| | 무엇인가 | 어디에 | 로컬에서 |
|---|---|---|---|
| `verifications` | 판정 기준 | config | 끄면 기록에 남고 게이트에 표시된다 |
| `skills` | 만드는 방식 | profile | 자유. 기록만 남는다 |

**검증은 판정 기준이라 사람마다 다르면 안 된다.**
같은 조건을 누구는 e2e 로, 누구는 눈으로 확인하면 “통과했다”가 서로 다른 뜻이 된다.

**스킬은 만드는 방식이라 달라도 된다.**
어차피 같은 판정을 통과해야 하기 때문이다.
사람마다 잘 쓰는 도구가 다르고, 업무 성격도 다르다.
새 스킬을 나 먼저 시험해보는 것도 여기서 일어난다.

**그래서 `profile.local` 은 예외 통로가 아니라 정식 기능이다.**

```json
// profile.local.json — 내 방식
{
  "skills": {
    "implement": { "type": "custom", "path": ".claude/skills/my-tdd" },
    "review":    { "type": "external", "url": "https://github.com/other/experimental-review" }
  }
}
```

```json
// config.local.json — 내 머신
{
  "verifications": [
    { "name": "e2e", "skip": true }
  ]
}
```

**판정하는 기준은 파일이 아니라 내용이다.**
`verifications` 를 끄면 어느 파일에서 껐든 경고고,
`skills` 를 바꾸면 어느 파일에서 바꿨든 정보다.

```
[Gate 3] ticket-3 을 완료로 볼 것인가

  verification   typecheck · lint · test   통과   ▸
                 e2e                       [!] 로컬에서 건너뜀

  skills         implement · review        [i] 로컬 설정
```

**“통과했다”와 “안 돌렸다”가 구분된다.**
그리고 기록에 남으니 나중에 “이 티켓은 e2e 없이 지나갔다”를 알 수 있다.

스킬 쪽은 경고가 아니라 정보 표시다. 문제가 아니라 사실이기 때문이다.

**명령과 경로는 자유다.**

누구는 pnpm, 누구는 npm. 맞추라고 강요할 이유가 없다.

```json
// config.local.json
{
  "verifications": [
    { "name": "test", "cmd": "npx vitest run" }
  ],
  "sync": {
    "records": { "token": "eyJ…개인 토큰" }
  }
}
```

**같은 파일 안에서도 성격이 갈린다.**
`cmd` 를 바꾸는 것은 자유고 `skip` 을 켜는 것은 경고다.
무엇을 덮었는지를 보고 판단한다.

### ~/.awl/config.json — 전역 기본값

```json
{
  "author": "hong@midasit.com",
  "sync": {
    "records":  { "endpoint": "https://internal.example/api", "token": "eyJhbGciOi..." },
    "feedback": { "endpoint": "https://internal.example/feedback" }
  }
}
```

**사람에게 속한 값만 여기 있다.** 신원과 자격증명이다.
저장소가 열 개여도 한 번만 쓴다.

`feedback` 은 토큰이 없다. 익명이어도 쓸모 있고 장벽을 낮춰야 실제로 쌓인다.
기본값이 하드코딩돼 있어 설정 안 해도 켜져 있다. 끄려면 `"feedback": false`.

**왜 `settings.json` 이 아닌가**

덮어쓰기 사슬은 이름을 공유해야 한다. `.env` → `.env.local` 이 그렇고,
git 은 system · global · local 세 스코프를 전부 `config` 라 부른다.
`~/.awl/settings.json` 이 `.awl/config.json` 에 덮이는 건 앞뒤가 안 맞는다.

그리고 토큰은 자격증명이고 `author` 는 신원이다.
`settings` 가 가리키는 "내가 어떻게 쓸지"가 아니라 **"이 기능이 돌려면 필요한 값"**이다.

**author 는 git config 를 씨앗으로 쓴다**

```
init 할 때    git config user.email 을 읽어 입력란을 미리 채운다
그 뒤로       config 만 읽는다. git config 는 안 본다
```

런타임에 git 을 안 부르니 결정적이다.
**git config 자체는 고치지 않는다.** 커밋 작성자까지 바뀌는 건 다른 문제다.

```
+- 작성자 ---------------------------------------------------------+
|                                                                  |
|  기록에 작성자로 남을 메일입니다.                                |
|  중앙에서 이 영역을 아는 사람을 찾을 때 쓰입니다.                |
|                                                                  |
|    > hong@midasit.com                                            |
|      git config user.email 에서 가져왔습니다. 고쳐도 됩니다.     |
|                                                                  |
|  ~/.awl/config.json 에 저장됩니다. 저장소마다 다시 묻지 않습니다.|
|                                                                  |
+------------------------------------------------------------------+
```

**없어도 막지 않는다.** 기록에 `author` 가 안 붙을 뿐이다.

### 어디서 온 값인지 보여준다

전역이 생기면 "이 값이 어디서 왔나"가 흐려진다. git 이 같은 문제를 이미 풀었다.

```
$ awl config --show-origin

  author       hong@midasit.com          ~/.awl/config.json
  endpoint     https://internal/api      ~/.awl/config.json
  repository   midasit/maxflow           .awl/config.json
  test.cmd     npx vitest run            .awl/config.local.json
```

### 병합 규칙

```
base → local 순. local 이 이긴다

객체    키 단위로 깊게 병합       config 의 verifications
배열    name 키로 병합            profile 의 verifications
비활성  skip: true
```

**배열을 통째로 갈아끼우지 않는다.**
e2e 하나 끄려고 목록 전체를 복사하게 하면 아무도 제대로 안 쓴다.

**`user.json` 은 두지 않는다.** `author` 가 전역 기본값을 갖게 되면서
덮을 짝이 생겼고, 그래서 평범한 config 필드가 됐다.

### state.json — 커밋 안 함

진행 상태와 모드가 들어간다. 지금 어느 티켓을 하고 있는지는 개인 것이다.

## 8. 모드

**프로파일 값이 아니다. 실행할 때 고른다.**

팀이 공유하는 설정이 아니라 그때그때 개인이 고르는 것이다.
같은 프로젝트에서도 오늘은 신중하게, 내일은 빠르게 갈 수 있다.

```
strict      모든 게이트에서 확인한다
semi-auto   요청을 열고 닫을 때만 확인한다        ← 기본
auto        전부 자동. 요청 닫을 때 요약만 받는다
```

**기본은 `semi-auto` 다.** 시뮬레이션에서 `strict` 는 티켓 5개에 11회를 멈췄다.
부담의 전부가 게이트 2·3인데 둘 다 기계 판정이 끝난 뒤에 묻는다.

`default` 라는 이름을 안 쓰는 이유는 그것이 기본이 아니게 됐기 때문이다.
**이름이 하는 일을 말해야 한다**는 규칙이 여기에도 적용된다.

플래그가 둘로 준다.

```
awl run "..."              semi-auto · 자가 검증
awl run --strict "..."     처음 쓰는 영역
awl run --auto "..."       신뢰가 쌓인 영역
awl run --review "..."     교차 검증을 켠다
```

`--review` 는 게이트 모드와 다른 축이다. 사람이 언제 멈추느냐와
검증을 누가 하느냐는 별개다.

**레인 단위 상태다.** 레인마다 성격이 다를 수 있다.
신뢰가 쌓인 영역은 `auto`, 처음 건드리는 영역은 `strict` 로 둔다.

**세션 중에 바꿀 수 있다.** 잘 돌아가는 게 보이면 올리고 이상하면 내린다.
**바꾼 것도 기록에 남는다.** "티켓 3까지는 strict 였고 그 뒤로 auto 였다"가 보여야
나중에 문제가 생겼을 때 어디부터 사람이 안 봤는지 안다.

**어느 모드든 자동 승인은 기록에 남는다.**
게이트를 없애는 게 아니라 사람 손을 빼는 것이다.

## 9. 게이트

### 네 개

```
요청 열림
  [1] 티켓을 확정한다        coverage: 이 티켓들로 요청이 만족되는가
     티켓 [2] 착수 ... [3] 완료
  [4] 요청을 닫는다          실제로 만족됐는가
요청 닫힘
```

층마다 여는 게이트와 닫는 게이트가 하나씩. 대칭이다.
**[1]과 [4]가 같은 질문을 앞뒤로 묻는다.** 사전 판정과 사후 판정이다.

### 접기 규칙

LLM 요약을 쓰지 않는다. **접기를 쓴다.**

> **승인을 바꿀 수 있는 것만 펼친다.**

```
접힘    통과한 검증 · 예상대로 된 스파이크 · 충족된 조건 · 읽은 파일 목록
펼침    실패 · 예상과 다른 것 · 제외한 것 · 리뷰 지적 · 정성 판정의 반대 의견
```

**요약보다 나은 이유**: 접힌 것도 거기 있다는 게 보인다.
`▸` 가 있으니 "검증 결과가 있긴 하구나"를 알고 필요하면 펼친다.
요약은 무엇이 빠졌는지 알 수 없다. 그리고 누가 접었는지가 규칙이라 예측 가능하다.

### 화면

```
[Gate 1] coverage 판정

  request        레이어 패널을 키보드로 조작하고 싶다
  domain         editor
  tickets        5  foundation 1 · feature 4        ▸
  dependencies   ticket-1 → ticket-2 → ticket-3     ▸

  out of scope   3
    다중 선택       ItemSelector 가 단일값
    드래그 재정렬    이번 요청과 무관
    포커스 트랩      접근성 작업으로 분리

  (*) 이대로 시작   ( ) out of scope 를 다시 논의   ( ) 중단
```

```
[Gate 2] ticket-3 방향키 이동을 시작한다

  condition-1     언제 포커스가 패널에 있고 위·아래 방향키를 누르면,
                  선택이 한 칸씩 이동해야 한다
  verification    e2e
                    given  레이어 패널에 포커스가 있다
                    when   아래 방향키를 누른다
                    then   aria-selected 가 다음 행으로 이동한다

  spike           2건 중 1건이 예상과 달랐다
    ✗ itemSelector 가 단일값이라 다중 선택 불가

  investigation   finding 3                          ▸

  (*) 착수   ( ) 계획을 다시   ( ) 중단
```

```
[Gate 3] ticket-3 을 완료로 볼 것인가

  verification   typecheck · lint · test · e2e   모두 통과   ▸
  commits        3                                          ▸

  review         지적 2건
    ! 키보드 이벤트가 input 안에서도 잡힌다        constraint 없음
      스펙 누락. 새 조건으로 편입, 통과함
    ! 테스트가 핸들러를 지워도 통과한다             constraint 없음
      구현 결함. 단언을 aria-selected 로 바꿈

  (*) 완료   ( ) 더 작업   ( ) 중단
```

```
[Gate 4] 요청을 닫을 것인가                        strict

  conditions     승인 때 3개 → 지금 4개             ▸
  out of scope   3 그대로                           ▸

  qualitative    맥락 모르는 리뷰어 3명 · 2회 반복
    ! 2명이 같은 지적: 포커스 위치가 시각적으로 안 보인다

  마무리
    병합    awl/keyboard-nav  →  feature/editor-rework
    정리    기록 전송 · 워크트리 제거 · 브랜치 삭제

  (*) 병합하고 마무리   ( ) 판정만 하고 병합은 나중에   ( ) 보류
```

**판정과 마무리를 한 자리에서 묻는다.**
"만족됐는가" 에 답했으면 그다음이 병합이다. 나눠 물으면 사람이 두 번 와야 한다.

**기준 브랜치는 main 이 아니다.** 레인을 열 때 서 있던 브랜치다.
보통은 개인 기능 브랜치이고, 레인 메타에 저장해뒀다가 거기로 되돌린다.

**두 번째 선택지가 필요하다.** 다른 레인을 기다렸다가 순서대로 넣고 싶을 때가 있다.

### 게이트를 건너뛴 만큼 마지막에 펼친다

`strict` 면 중간에서 다 봤으니 Gate 4 를 접는다.
`semi-auto` 이하면 펼친다. 완료 티켓 목록, 각 티켓의 조건, 검증 방법 전체,
자동 승인 횟수까지.

## 10. 검증

### 세 층

| 레이어 | 무엇 | 어디 |
|---|---|---|
| binary | 기능이 되는가. 참거짓 | 티켓 |
| quantitative | 처리량, 지연시간, 오류율 | 요청 (회귀 감시는 티켓) |
| qualitative | 사용성, 직관성, 일관성 | 요청 |

**가르는 기준: 그 판정이 조각 하나로 성립하는가.**

임의가 아니라 티켓 도출 규칙에서 파생된다.
조각 하나로 판정이 안 되면 애초에 티켓 레벨에 있으면 안 된다.

아래 두 층은 조건부다. 스펙 단계에서 필요 여부를 판정한다.

### 기본은 자가 검증이다

**서브에이전트를 안 띄운다.** 같은 세션이 만들고 같은 세션이 검증한다.
`loop` 도 `pipeline` 도 단일 세션으로 끝난다.

핸드오프 비용이 얻는 것보다 크다는 판단이다.
넘기는 쪽이 갖고 있던 이해와 finding 을 받는 쪽이 다시 만들어야 하는데,
그 값이 리뷰가 잡아주는 것보다 비쌌다.

### 자가 검증이 할 수 있는 것과 없는 것

```
할 수 있다    조건 ↔ 검증 ↔ 커밋이 대응하는가
              제약을 어긴 것이 있는가
              테스트가 구현을 지워도 통과하는가

할 수 없다    이 구현이 적절한가
              더 나은 방법이 있는가
              놓친 경우가 있는가
```

**위쪽은 기계적 대조라 누가 하든 답이 같다.** 자기가 썼든 아니든 상관없다.

**아래쪽은 편향이 답을 바꾼다.** 방금 자기가 쓴 코드를 보면서
"이게 맞나"를 물으면 맞다고 판단할 이유를 찾는다.
틀렸다고 하려면 방금 한 일을 부정해야 한다.

### 안 본 것은 안 봤다고 남긴다

```
verification   typecheck · lint · test   통과
self-check     조건 대응 · 제약 · 부존재   통과
review         안 함                      [-]
```

**조용히 통과시키지 않는다.**
나중에 문제가 생겼을 때 그 구간이 교차 검증을 안 거쳤다는 것이 보여야 한다.

`[-]` 는 실패가 아니라 안 한 것이다. sync 가 꺼져 있을 때와 같은 표시다.

### 부존재 탐지는 자가 검증에서도 성립한다

```
자기 커밋을 지우고 테스트가 통과하는지 본다
```

**기계적이라 편향이 도움이 안 된다.** 통과하면 그 테스트는 아무것도 안 재고 있는 것이다.

실사용에서 겪은 "테스트가 핸들러를 지워도 통과한다" 류를 이걸로 잡는다.
같은 세션이 해도 결과가 같으므로 기본으로 켜둔다.

### 켜려면 --review

```
awl run --review "..."
```

편향이 문제되는 판단이 필요할 때 쓴다.
되돌리기 어려운 변경이거나, 처음 건드리는 영역이거나, 전부 한 번에 통과했을 때다.

**전부 1차 통과에 막힘 0 은 축하할 일이 아니라 의심할 일이다.**
완료 조건이 사소했다는 신호일 수 있고, 그건 자가 검증으로 못 잡는다.

### --review 를 켰을 때

**세션 수와 리뷰 단위는 다르다.**

```
티켓마다 세션 하나       세션 N개 · 리뷰 대상 작음
세션 하나가 순차로 본다   세션 1개 · 리뷰 대상 여전히 작음   ← 이쪽
```

리뷰어 세션 하나가 커밋을 하나씩 본다. 스폰은 한 번이고 대상은 커밋 단위다.
diff 를 통째로 던지면 안 된다. **400줄이 넘으면 정확도가 급격히 떨어지고
1000줄이면 고무도장이 된다.**

**맥락을 안다고 편향이 생기지는 않는다.**
"맥락 모르는 눈"이 중요한 건 구현자의 편향을 안 물려받는다는 뜻이지
코드를 처음 본다는 뜻이 아니다.

```
기반 티켓    conditions: []      다른 티켓이 그 위에 쌓인다  →  즉시
기능 티켓    conditions: [x]     독립적이다               →  마지막에 모아서
```

재리뷰는 고친 커밋만 본다. **2회로 끊고** 그래도 안 되면 사람을 부른다.

### 리뷰어에게는 재료를 싸서 준다

리뷰어가 비싼 진짜 이유는 스폰이 아니라 **맥락 없이 시작해 코드베이스를 탐색하는 것**이다.

```
부트스트랩         5~10k
코드베이스 탐색    20~50k    ← 여기가 크다
재료 읽기          5k
판단 출력          2k
```

재료를 직접 주고 탐색을 막으면 10~15k 로 떨어진다.

```
$ awl review pack ticket-3

  조건 · 제약 · diff · 파일 목록 · finding · 검증 결과
```

```
아래 재료만으로 판단한다.
파일을 추가로 열지 않는다.
재료가 부족해 판단할 수 없으면 "재료 부족: <무엇>" 이라고 답한다.
```

**마지막 줄이 중요하다.** 탈출구가 없으면 모르면서 통과시킨다.
그리고 "재료 부족" 이 나올 때마다 팩에 무엇을 더 넣어야 하는지 알려준다.

### 정성 루브릭

점수 척도가 아니라 **판단이 필요한 이진 질문 목록**이다.

```markdown
## Qualitative
- 키보드만으로 패널의 모든 노드에 도달할 수 있는가
- 지금 어느 노드가 선택됐는지 시각적으로 알 수 있는가
```

"1~5점으로 평가해줘"라고 하면 대부분 4점이 나오고, 4점이 무슨 뜻인지 아무도 모른다.
yes/no 면 명확하고, no 가 나오면 구체적 지적이 따라온다.

**맥락 모르는 서브에이전트가 답한다.** 최종 결과만 사람에게 노출하고
문제가 있으면 게이트 4 에서 수정한다.

### 반증 요구

"괜찮아 보인다"는 검증이 아니다.
**만든 모델이 판정하면 의미가 없다.** 맥락을 모르는 서브에이전트를 띄운다.

```
교차 모델        판정자를 다른 벤더로. 호스트는 파트너 출력을 안 보고 독립 분석
적대적 페르소나   각각 최소 하나는 반드시 찾게. 통과로 빠져나갈 수 없게
패널 토론        여러 리뷰어가 토론하고 최종 판정자가 결론
```

부존재도 여기서 본다. "이 변경을 통째로 지우면 무엇이 깨지나."

**언제 돌리나**

기본은 안 돈다. `--review` 를 켰을 때 요청을 닫으며 한 번,
정성 루브릭이 붙었으면 반드시.

티켓 레벨은 트리거가 걸릴 때만. 하나라도 해당하면 돈다.

```
되돌리기 어렵다 (그 티켓에서 decision 이 나왔다)
기계 판정 비율이 낮다
전부 1차 통과에 막힘 0 (너무 쉬웠다는 신호)
이 영역에 gotcha 가 쌓여 있다
변경 범위가 크다
```

### 모델은 프로파일에 안 쓴다

가용 목록도 결국 상한다. 모델이 폐기되면 프로파일이 못 도는 상태가 되고,
공유받은 프로파일이 더 위험해진다.

**파이프라인 스킬을 실행한 모델이 상한이다.**
자기보다 나은 걸 고를 수는 없다. 뭐가 더 나은지 모르니까.
더 가벼운 걸 고르는 건 판단이 된다. 세 줄짜리 티켓은 가볍게, 아키텍처를 건드리면 같은 급으로.

**다른 벤더는 실행 시점에 환경에서 감지한다.** 설치된 CLI 를 보면 나온다.

### 리뷰 지적이 조건을 늘리면

```
구현 결함    티켓 안에서 고친다. 스펙 안 건드림
스펙 누락    조건을 추가하되 게이트 1 을 다시 안 거친다
             게이트 4 에서 "승인 때 3개 → 지금 4개"로 보여준다
```

**가르는 기준은 "스펙대로 했는데도 문제인가"다.**

게이트 1 로 되돌아가지 않는 이유는 흐름이 끊기고,
추가는 축소보다 안전하기 때문이다. 커버리지가 줄지 않는다.

## 11. 저장

### 세 층

```
개인 PC 워킹 카피  →  부서별 git remote(여러 개)  →  전사 중앙(하나)
```

**원본은 git 저장소, 중앙은 사본과 색인.**

git remote 는 부서 단위라 전사로 보면 서로 다르다.
그래서 전사 중앙이 부서 간 시행착오 중복을 막는 유일한 통로다.

### 중앙 구조

```
중앙/
  docs/<owner>/<repo>/
    CONTEXT.md
    specs/20260725-143052-....md
    decisions/20260725-160841-....md

  profiles/*.json             공유 프로파일

  records/<owner>/<repo>/2026-07.jsonl

  index.db                    위에서 재생성
```

**경로를 git remote 에서 유도한다.**
프로젝트 이름은 자연스럽게 겹친다(dashboard, admin, api).
전사 유일 slug 를 강제하면 마찰만 생기고, remote 기반이면 충돌이 구조적으로 불가능하다.
등록 절차도 필요 없다.

**조직개편과 무관하다.** 팀이 바뀌어도 저장소는 그대로 있다.
소유 팀은 프론트매터의 `organization` 에 남는다.

**문서는 파일 그대로, 기록은 JSONL, 색인은 재생성 가능하게.**
중앙을 git 저장소로 두면 revision 이력이 공짜로 생긴다.
POST 받으면 파일 쓰고 커밋만 하면 된다.

### author — 누가 아는지를 중앙에서 찾는다

```
records                author 필수     사건마다 쌓인다
spec · ticket · decision   author 생성자   누가 시작했나
feedback               안 넣는다       보류
```

**목적은 중앙에 물었을 때 이 영역을 아는 사람이 바로 나오는 것이다.**

저장소로 넘어가 `git log` 를 보는 방식은 안 된다.
느리기도 하지만 **저장소를 가로지르는 집계가 안 된다.**
"editor 도메인을 가장 많이 다룬 사람"을 알려면 저장소 열 개를 각각 훑어야 한다.
중앙에 모아둔 의미가 사라진다.

**기록이 주력이다.**

```
spec       누가 시작했나              건수가 적다
records    누가 이 영역에서 일했나     건마다 쌓인다
```

스펙 하나를 A 가 썼어도 실제로 파고든 사람은 티켓을 돌린 B 일 수 있다.
기록은 사건마다 남으니 실제 관여도가 그대로 드러난다.

**문서의 author 는 생성자로 고정한다.**
수정 이력은 기록이 담는다. B 가 손대면 B 의 기록이 쌓이므로
문서에 기여자 목록을 따로 관리할 필요가 없다.

**"가장 많이 안다"를 무엇으로 셀지는 아직 안 정했다.**
지금은 구분해서 쌓아두기만 한다. 데이터가 쌓인 뒤에 정한다.

### 로컬이 먼저다

원격 전송이 실패해도 루프가 멈추면 안 된다.
사내 서버가 잠깐 죽었다고 개발이 멈추는 구조는 쓰이지 않는다.

로컬에 먼저 쓴다. 원격은 그다음이다.

### 큐가 아니라 커서다

**기록은 이미 로컬 파일이다.** 보낼 것을 따로 복사해 쌓을 이유가 없다.

```
state.json 의 커서    여기까지 보냈다
```

보내면 커서가 앞으로 가고, 실패하면 커서가 그 자리에 있는다. 그뿐이다.

### endpoint 가 없으면 아무것도 안 한다

```
endpoint 없음    전송 기능이 꺼진 상태다
                 커서를 만들지 않는다. 재시도도 없다
                 기록은 로컬에만 남는다
```

**나중에 설정하면 그 시점부터 시작한다.** 이전 것을 소급해서 보내지 않는다.

보내기로 한 적이 없는 기록이 어느 날 갑자기 중앙에 나타나면 놀란다.
그리고 몇 달치가 한 번에 올라가면 시점이 뒤엉킨다.

정말 필요하면 로컬 파일이 그대로 있으므로 그때 명시적으로 보내면 된다.

### endpoint 가 있는데 실패하면

```
지수 백오프    1분 → 5분 → 30분 → 2시간 → 6시간 → 하루
7일 경과       커서를 앞으로 밀고 로그만 남긴다
```

**7일인 이유는 디스크가 아니라 맥락이다.**
서버가 죽었으면 일주일 안에 누가 눈치챈다.
그보다 오래 방치된 기록은 지금 올라가도 의미가 없다.

**포기할 때 로그를 남긴다.** "이 기간에 N건이 중앙에 안 갔다"를 알아야
나중에 데이터가 비어 있는 이유를 안다.

### API

```
POST   /records      기록 전송 (멱등)
POST   /specs        스펙 등록
GET    /specs        목록 (프론트매터만)
GET    /specs/:id    전문
GET    /specs?q=     검색
```

| 무엇 | 필요한 것 | 이유 |
|---|---|---|
| 기록, 경험 | POST | append-only. 조회는 로컬에서 |
| **스펙** | **POST + 조회** | 다음 사람이 참조해야 한다 |

**멱등성**: `revision` 이 같으면 이미 받은 것으로 보고 무시한다.

**검색과 목록은 다르다.** 프론트매터/본문 구분은 "목록에 무엇을 보여줄까"지
"무엇을 검색할까"가 아니다. 색인은 둘 다 한다.

### 인증

**조직 단위 JWT.** 서버가 토큰으로 organization 을 판정한다.
프로파일은 사람이 손으로 고칠 수 있는 파일이라 신뢰 근거로 쓰지 않는다.

```json
{
  "iss":     "awl",
  "org":     "platform-lab",
  "orgName": "플랫폼실",
  "ver":     3,
  "iat":     1784000000,
  "exp":     1815536000
}
```

**폐기는 토큰 버전으로 한다.** 서버가 조직별 현재 버전을 갖고 있고,
토큰의 `ver` 가 다르면 거부한다. 유출되면 버전을 올리고 새 토큰을 발급하면
이전 것 전부 무효다. 블랙리스트와 달리 목록이 안 커진다.

**만료는 6개월.** 로컬 우선 설계라 토큰이 죽어도 개발은 안 멈춘다.
커서가 멈춰 있을 뿐이고, 7일 안에 갱신하면 밀린 것이 함께 나간다.

**토큰은 `~/.awl/config.json` 에 있다.** 커밋되는 파일에 비밀이 없다.

발급받아 넣는 권한이므로 사람에게 속한다. Claude Code 가 인증을 전역에 두는 것과 같다.
저장소를 클론해도 토큰은 안 따라오고, 사람마다 평생 한 번 설정한다.

### awl init

```
+- 기록 위치 ------------------------------------------------------+
|  기록이 저장될 위치를 선택하세요.                                |
|  개선을 지속하기 위한 데이터의 기반이 됩니다.                    |
|                                                                  |
|    (*) 플랫폼 중앙    https://internal.example/api               |
|    ( ) 데이터 중앙    https://data-internal/api                  |
|    ( ) 직접 입력                                                 |
+------------------------------------------------------------------+

+- 토큰 -----------------------------------------------------------+
|  기록 위치에 쓰기 권한을 가진 토큰을 입력하세요.                 |
|  없으면 관리자에게 요청하세요.                                   |
|                                                                  |
|    > ..............................                              |
|                                                                  |
|  이 값은 .awl/config.json 에 저장되고 커밋됩니다.                |
|  건너뛰면 기록이 로컬에만 쌓입니다. 나중에 넣어도 됩니다.        |
+------------------------------------------------------------------+
```

**endpoint 목록만 하드코딩한다.** 토큰은 절대 하드코딩하지 않는다.
npm 에 공개 배포되므로 패키지를 까면 나온다.

이 값들은 `~/.awl/config.json` 의 `sync.records` 로 들어간다. 저장소에는 안 남는다.

목록은 나중에 네트워크로 받아온다.

**건너뛸 수 있어야 한다.** 토큰이 아직 없어도 설정이 막히면 안 된다.
로컬 우선 원칙이 여기서도 그대로다.

**둘 다 평생 한 번이다.**

```
사람마다 한 번     전역 설정. 토큰과 신원
저장소마다 한 번   프로젝트 설정. 검증 명령과 프로파일
```

Claude Code 를 쓰는 방식과 같다.
`~/.claude` 에 한 번 설정하고 프로젝트마다 `.claude` 를 두는 것과 같은 모양이다.

### 피드백

도구 자체의 오류와 엣지 케이스를 자동으로 수집한다.
**기본은 켜져 있다.** 무조건 쌓는 쪽이 맞다. 안 쌓이면 개선할 재료가 없다.

```
들어간다    도구 오류와 스택 트레이스
            명령 실패와 종료 코드
            예상 못 한 상태 (엣지 케이스)
            최소 맥락 — 어떤 명령을, 어느 단계에서, 어느 상대 경로에서
            사람이 명시적으로 남긴 개선 제안

안 들어간다  코드 내용
            스펙과 티켓 본문
            토큰과 인증 정보
            절대 경로 (저장소 루트 기준 상대 경로만)
```

**LLM 이 판단해서 정리한 형태로 보낸다.** 로그를 통째로 던지지 않는다.
무엇이 문제였는지와 최소 맥락만 남기면 개인정보 노출면도 같이 줄어든다.

**사람이 남기는 건 `awl feedback "..."` 으로 한다.**
자동 수집만으로는 "이게 불편하다"가 안 잡힌다.

그리고 이 자리가 있으면 쓰는 사람이 **도구를 함께 만든다고 느낀다.**
불편이 하나씩 해결되는 게 보이기 때문이다.
그래서 반영된 피드백은 되돌려 알리는 게 좋다.

## 12. 쌓이는 것의 관리

### 초반에는 쌓기만 한다

상한도 승격도 두지 않는다.
지금 제약이 몇 개나 쌓일지, 어떤 종류가 많을지, 검사 가능한 비율이 얼마일지 모른다.
**관찰 안 된 문제에 규칙을 만들면 엉뚱한 데를 조인다.**

### 나중에 정리할 수 있게 쌓는다

"나중에 정리하자"는 대개 안 한다. 정리에 필요한 정보를 지금부터 붙여둔다.

```
source    어느 기록에서 왔나
hits      실제로 몇 번 걸렸나
```

**`hits` 가 핵심이다.** 나중에 판단이 필요 없어진다.

```
hits 0      한 번도 안 걸렸다. 버릴 후보
hits 높음   계속 걸린다. 검사기로 만들 후보
```

### hits 를 어떻게 세나

검사기가 잡는 건 자동으로 센다.

리뷰어가 잡는 경우, **리뷰어는 지적할 때 어느 제약인지 반드시 지목한다.**
해당하는 게 없으면 "없음"이라고 명시한다. 그러면 새 제약 후보가 된다.

### 정리

쌓인 것을 보고 무엇을 버리고 무엇을 올릴지 정하는 자리다.
애자일의 회고에 해당하는데 다루는 게 다르다.
회고는 "우리가 어떻게 일했나"를 보고, 이건 **"쌓인 게 무엇을 말하나"**를 본다.

```
신호가 뜬다        3회 반복된 승격 후보 30개 초과
       ↓
정리                모여서 본다
       ↓
결정한다            버릴 것 · 검사기로 만들 것 · 규칙으로 올릴 것
```

**정기가 아니라 신호 기반이다.**
정기로 두면 볼 게 없는데 모이거나, 바쁘면 건너뛴다.
신호가 쌓이면 모이고 없으면 안 모인다.

### 신호는 좁게, 기록은 넓게

**세는 것은 3회 반복된 승격 후보뿐이다.**

```
3회 반복된 clarification    decision 승격 후보
3회 반복된 정량 지표         형식을 정할 후보
```

`hits 0` 인 제약이나 용어집 밖 용어도 **기록은 하지만 신호에 안 넣는다.**
반복되지 않은 건 정리 가치가 아직 없어서 노이즈만 만든다.

모여서 볼 때는 그것들도 함께 본다. 소집 명분에만 안 쓸 뿐이다.

### 누적이 아니라 증분이다

```
지난 정리 이후 쌓인 것이 30건 넘으면 알림
```

**누적으로 두면 정리를 해도 총량은 그대로라 계속 뜬다.**
증분이면 정리 후 카운터가 리셋된다.

### 알림

```
  [!] 3회 반복된 승격 후보가 31건 쌓였습니다.
      마지막 정리 2026-05-12

      clarification 반복   24건
      정량 지표 반복        7건

      함께 볼 것
        제약 hits 0        14건
        용어집 밖 용어      6건

      awl backlog 로 목록을 봅니다.
      누구든 회의를 소집할 수 있습니다.
```

**마지막 줄이 중요하다.** 리더가 소집하는 게 아니라 알림 자체가 명분이 되어야 한다.
안 그러면 아무도 안 한다.

**스킬 부트스트랩 시 표시한다.** 그러면 그 프로젝트를 쓰는 사람 전원이 보고,
누구든 먼저 말을 꺼낼 수 있다.

### 별도 문서를 안 만든다

정리의 산출물은 기존 것들의 변경이다.
제약이 지워지고, 규칙이 생기고, 용어집이 갱신된다.
git 히스토리에 남으니 따로 기록할 게 없다.

### domain

자유 문자열이되, 그 프로젝트에 없던 값을 쓰면 게이트에 표시한다.

```
domain   editors                                   [!]
  이 프로젝트에 없던 domain 입니다.
  기존: editor, gallery, auth
  새로 만드는 게 맞습니까?
```

프로파일에 목록을 강제하지 않는다. 새 도메인마다 프로파일 수정이 부담이 되면
아무거나 있는 걸 골라 쓰게 되고, 그게 더 나쁘다.

**domain 이 중요한 이유**는 스펙 자동 로드가 이걸로 좁히기 때문이다.
값이 갈라지면 자동 로드가 조용히 반쪽이 된다.

## 13. 기법이 붙는 자리

### 역할 역전 (grill)

| | spec | clarification |
|---|---|---|
| 대상 | 목표와 요구 | 이번 계획 |
| 코드 | 없거나 무관 | 이미 있다 |
| 산출물 | 문서로 남는다 | 티켓에 남는다 |
| 핵심 규칙 | 반드시 남긴다 | 코드로 답할 수 있으면 묻지 않는다 |

**진단**: "코드를 읽으면 답이 나오는가"라는 질문 자체가
성립하면 clarification, 성립 안 하면 spec.

**안 붙는 자리도 정해둔다.** 안 그러면 모든 단계에 질문이 붙어 사람이 지친다.

```
만들 것을 정할 때    사람도 모르는 것이라 spike 로 판정
끝을 정의할 때       앞에서 다 물었으면 번역만 남는다
게이트 이후          자율 구간
```

**물을 게 없으면 건너뛰고 "없음"을 남긴다.**
억지 질문을 만들면 사람이 지치고 다음부터 대충 답한다.
물을 게 없었던 것과 안 물은 것은 구분되어야 한다.

### 조사 (investigation)

산문이 아니라 목록이다.

```
finding-1  키보드 핸들러가 LayersPanel 밖에 있다
           source: investigation
           where:  keyboard.tsx:42

finding-2  Row 와 Stack 에서 auto 높이가 다르게 렌더된다
           source: spike
           result: 예상과 다름
```

**spike 결과도 finding 으로 합친다.** 둘 다 "알게 된 사실"이고
알게 된 방법만 다르다. 목록이 하나면 다음 사람이 한 곳에서 찾고 재사용도 쉽다.

예상대로 된 spike 도 남긴다. 다음 사람이 다시 확인 안 해도 되니까.
게이트에서는 접힌다. **spike 코드 자체는 버린다.**

**종료 판정**: 티켓의 조건을 건드리는 코드 경로가 전부 목록에 있으면 끝이다.

```
condition-1  방향키로 선택 이동
  → 키보드 이벤트가 들어오는 곳
  → 선택 상태를 갖는 곳
  → 선택을 그리는 곳
```

조건이 EARS 라 입력 경로와 출력 경로가 문장에서 도출된다.
개수나 파일 수로 정하지 않는다. 세 개를 아무거나 찾아도 통과하면 의미가 없다.

**다음 단계가 원본을 다시 안 읽는다.** 이 목록만 근거로 쓴다.

### 이미 아는 것을 먼저 준다

시뮬레이션에서 `investigation` 이 토큰의 29% 를 먹었고 상당 부분이 중복이었다.
`ticket-1` 이 만든 finding 이 `ticket-3·4·5` 에서 재사용되지 않았다.

```
$ awl next

  stage       investigation
  ticket      ticket-4  접기·펼치기

  known       finding 6건 (ticket-1, ticket-2, ticket-3 에서)
    finding-1  키보드 핸들러가 LayersPanel 밖에 있다   keyboard.tsx:42
    finding-2  tabindex 관리가 없다                   LayersPanel.tsx:203  [확인 필요]
    finding-5  선택 인덱스는 useLayerState 가 갖는다   state.ts:71

  위 finding 은 이미 확인됐다. 다시 찾지 않는다.
  condition-2 를 건드리는 경로 중 위에 없는 것만 조사한다.
```

**새 저장소가 필요 없다.** 같은 스펙의 티켓들에서 finding 을 모아 넘기기만 하면 된다.

`[확인 필요]` 는 그 finding 이 가리키는 파일이 그 뒤 커밋에서 바뀌었다는 뜻이다.
줄 번호가 밀렸을 수 있다.

**여기서 일반 규칙이 하나 나온다.**

> 세션이 시작할 때 이미 아는 것을 먼저 준다.

리뷰어 재료 팩도 finding 재사용도 같은 규칙이다.
**탐색은 모를 때만 하는 것이다.**

## 14. 레인과 병렬

### pipeline 은 loop 를 여러 개 돌리는 것이다

둘이 다른 물건이 아니다. 차이는 하나뿐이다.

```
loop        요청 하나. 티켓이 몇 개든 순서대로
pipeline    요청 여러 개를 동시에. 서로 안 섞여야 한다
```

**티켓이 많은 건 loop 로 충분하다.** 의존 순서대로 처리하면 된다.
pipeline 이 필요한 건 서로 무관한 요청 여럿을 같은 날 돌릴 때다.

```
awl run "레이어 패널 키보드 조작"                          레인 하나
awl run --lanes "키보드 조작" "인증 리프레시" "번들 축소"    레인 셋
```

### 서브에이전트는 맥락을 끊어야 할 때만 띄운다

끊을 이유가 셋뿐이다.

```
편향을 피해야 한다    리뷰 · 반증 요구. 만든 사람이 보면 못 본다
동시에 해야 한다      레인. 한 세션이 세 워크트리를 동시에 못 다룬다
오염되면 안 된다      다른 레인의 코드가 섞이면 안 된다
```

**구현은 어디에도 안 걸린다.** 스펙을 만든 세션이 그대로 구현하면 된다.
검증도 마찬가지다. 기본은 자가 검증이고 `--review` 를 켰을 때만 하나 띄운다.

plan · exec · review 로 나눴던 건 사람 조직을 그대로 베낀 것이다.
사람 팀에서 역할을 나누는 이유는 한 사람이 다 못 하기 때문인데 에이전트는 다 할 수 있다.
**역할 이름이 다르다는 게 세션을 나눌 근거가 아니었다.**

핸드오프가 잃는 게 크다.

```
넘기는 쪽이 갖고 있던 것     스펙을 만들며 얻은 이해
                            왜 이 티켓인지
                            이미 읽은 파일과 finding
                            사람이 게이트에서 뭐라고 했는지

받는 쪽이 받는 것            일감 문서 한 장
```

**나머지를 다시 만드느라 토큰을 쓰고, 다시 만든 이해가 원래와 미묘하게 달라 실수도 난다.**

자동 압축이 재부트스트랩보다 싸다. 압축은 무엇이 중요했는지 아는 상태에서 줄이고,
새 세션은 그 정보가 없어서 다 읽어야 한다.

### 무엇을 격리하고 무엇을 공유하나

```
격리한다    .awl-worktrees/<lane>/    git worktree + 브랜치 awl/<lane>
            state.json                워크트리마다 따로. 자동으로 갈라짐
            포트                       레인마다 오프셋

공유한다    config.json · profile.json  설정은 하나여야 한다
            기록 · gotcha · finding      읽기는 전부. 쓰기만 나눈다
```

**격리해야 하는 건 코드지 학습이 아니다.**
개인 저장소까지 격리하면 레인 A 가 겪은 실패를 레인 B 가 모른다.
같은 시행착오를 레인 수만큼 반복하고, 병합은 정리 때야 일어나니 그때는 늦다.

### 학습 공유는 파일을 나눠서 푼다

워크트리는 파일이 분리되니 그냥 두면 기록도 갈라진다.
**주 워킹카피의 `.awl/records/` 하나를 가리키게 한다.**
`git worktree list` 의 첫 항목이 주 워킹카피다.

쓰기 경합은 파일명으로 없앤다.

```
.awl/records/2026-07.jsonl                레인 없을 때
.awl/records/2026-07.keyboard.jsonl       레인 있을 때
.awl/records/2026-07.auth.jsonl
```

**읽을 땐 전부 훑고 쓸 땐 자기 파일에만.**
경합이 없고 공유되고, 정리 때 병합할 것도 없어진다.

### 세션당 레인 하나

**오케스트레이터 에이전트를 안 띄운다.**

```
awl lane new keyboard auth bundle    worktree · 브랜치 · 포트만 만든다
                                     기준 브랜치를 레인 메타에 저장
    ↓
사람이 터미널 셋을 열고 각각 /awl 을 돈다
각 세션이 spec 부터 검증까지 혼자 끝낸다
    ↓
awl lanes                            상황을 한눈에 본다
    ↓
awl lane rm <name>                   미머지 커밋이 있으면 거부
```

**시뮬레이션에서 세 세션이 동시에 사람에게 물어 정신없었다.**
레인마다 터미널이면 출력이 안 섞이고, 사람은 어차피 하나씩 처리한다.

그리고 awl 이 에이전트를 안 띄우게 된다.
**판단도 안 하고 스폰도 안 하는 것이 원칙과 더 맞는다.**
시뮬레이션에서 오케스트레이터가 1.2% 였는데 그것도 0이 된다.

터미널 관리는 사람의 몫이다. 레인이 많아지면
`awl lane new` 가 tmux 창을 열어주는 정도로 두면 된다.

레인 안에서 핸드오프가 없으므로 세션 간 일감 큐도 필요 없다.
티켓을 의존 순서대로 처리하면 된다.

### 포트가 진짜 충돌 지점이다

dev 서버와 e2e 브라우저가 같은 포트를 쓰면 부딪힌다.

```
lane 0    PORT=3000  PW_PORT=9323
lane 1    PORT=3010  PW_PORT=9333
lane 2    PORT=3020  PW_PORT=9343
```

awl 이 검증 명령에 환경변수로 주입한다.
**다만 프로젝트가 그 변수를 읽어야 한다.** 안 읽으면 못 나눈다.

그래서 안전장치를 둔다.

```json
{ "name": "e2e", "exclusive": true }
```

**`exclusive` 면 레인이 여럿이어도 그 검증만은 한 번에 하나씩 돈다.**
락 하나로 직렬화하면 포트를 못 나누는 프로젝트에서도 안전하다.

### 조용히 갈라지는 건 코드가 아니다

레인 둘이 같은 파일을 고치면 병합할 때 git 이 잡는다.
**문제는 관례가 갈라지는 것이다.**

레인 A 가 에러 처리를 이렇게 정하고 B 가 저렇게 정하면
코드는 안 부딪히는데 프로젝트가 두 갈래가 된다.

**그래서 뼈대 결정은 레인을 열기 전에 확정해야 한다.**
`docs/decisions/` 가 이미 공유되니 각 레인이 그것을 읽고 시작한다.

### 레인 수에 상한을 둔다

토큰이 레인 수에 비례해 나간다. 기본 상한을 두고 넘으면 확인받는다.

## 15. 토큰 집계

### awl 은 토큰을 직접 못 센다

쓰는 건 에이전트고 awl 은 파일과 상태만 만진다.
그런데 awl 이 이미 갖고 있는 것이 하나 있다. **시각이다.**

```
awl 기록      ticket-3  시작 14:30:52  →  종료 14:47:11
세션 로그      그 구간 메시지들의 usage 합
```

**구간으로 자르면 티켓별로 나온다.** 한 세션이 티켓 다섯 개를 처리해도 나뉜다.
단계도 같은 방법으로 나뉜다. 단계 전환마다 기록을 남기기 때문이다.

### 무엇을 보여주나

```
$ awl tokens ticket-3

  총              82,400
    investigation  31,200   38%
    implement      28,900   35%
    review         13,200   16%
    verify          9,100   11%
```

**이 표가 나오면 어디가 큰지 바로 보인다.**

```
investigation 이 크다     finding 재사용이 답이다
review 가 크다            재료 팩이 답이다
부트스트랩이 크다          세션 수를 줄이는 게 답이다
```

감으로 고르지 않게 된다.

### 레인별로도 본다

레인 셋을 돌렸을 때 합이 loop 하나의 세 배보다 얼마나 큰지가 병렬화의 실제 대가다.
**그 숫자가 사다리를 언제 올라갈지 정한다.**

### 주의

**캐시 읽기는 싸다.** 그냥 합치면 실제 비용과 어긋난다.
처음엔 raw 로 보되 `input / output / cache` 를 나눠 남겨두면 나중에 가중치를 붙일 수 있다.

### 어디에 두나

프로토타입 동안은 awl 안에 둔다. 지금 필요한 건 개선의 재료지 깔끔한 경계가 아니다.

**다만 세션 로그를 읽는 부분은 한 파일로 몰아둔다.**
외부 도구의 내부 형식에 의존하므로 바뀌면 깨진다. 몰아두면 거기만 고치면 되고,
나중에 별도 도구로 떼기도 쉽다.

## 16. 개선 포인트

지금은 안 하고 나중에 여는 것들.

- **"가장 많이 안다"의 기준** — 스펙 작성 건수 · 기록 건수 · 결정 건수 중
  무엇으로 셀지. 하나로 순위를 매기면 그 지표에 맞춰 행동이 바뀌므로
  나란히 보여주고 사람이 고르게 하는 쪽이 나을 수 있다
- **피드백의 author** — 지금은 안 넣는다. 넣으면 반영됐을 때 알려줄 수 있지만
  이름이 붙으면 "이런 것까지 보내도 되나" 하고 주저하게 된다.
  사람이 명시적으로 남긴 것에만 붙이는 절충안이 있다
- **skills 배열 확장** — 자리당 하나에서 조합으로.
  그때 조합 규칙(순차·병렬·충돌 시 우선순위)을 함께 정해야 한다
- **사내 인증 연동** — CLI 가 토큰을 그때그때 발급받게 하면
  버전을 올려도 다음 실행에 자동 갱신된다. 수동 배포가 사라진다
- **profiles 분류** — 카테고리·태그별 디렉토리
- **CI 연동** — 지금은 개인 PC 에서 직접 POST
- **Electron 앱** — 지금은 터미널 기반

## 17. 구현 순서

전부 한 번에 하지 않는다. 여섯 단계로 나누고 단계마다 실사용으로 검증한다.
자세한 작업 계획은 `adk-prototype.md` 에 있다.

### 1 · 문서 구조

스펙 · 티켓 · 결정 · 용어집이 파일로 생긴다. 중앙은 아직 없다.

```
awl doc new spec|ticket|decision <제목>
awl doc lint
```

**나머지 전부가 여기 의존한다.** 스펙이 없으면 티켓도 게이트도 없다.

검사기가 잡는 것: EARS 문형 · 질적 표현 · 스펙 본문의 파일 경로 ·
파일명 형식 · 용어집의 금지어.

### 2 · 티켓과 게이트

스펙에서 티켓이 도출되고 게이트 네 개가 실제로 멈춘다.

```
awl tickets derive <spec-id>
```

기존 게이트 둘을 넷으로 늘리고 `layer` 필드(`request` / `ticket`)를 붙인다.
접기 규칙과 세 모드(`strict` / `semi-auto`(기본) / `auto`)를 여기서 넣는다.

**절차가 실제로 멈추는지 여기서 판명된다.**

### 3 · 중앙 저장소

스펙과 기록이 중앙에 쌓인다. 서버가 죽어도 루프는 돈다.

임시 서버는 `localhost:9999`. **디렉토리에 파일만 쓴다.** DB 도 색인도 아직 없다.

```
POST /records  POST /specs  POST /feedback
GET  /specs    GET /specs/:id  GET /specs?q=
GET  /profiles GET /profiles/:name
```

스펙은 `closed` 가 될 때만 보낸다. 인증은 안 한다.

**쌓인 것이 밖으로 나가는지, 서버가 죽어도 도는지를 본다.**

### 4 · 프로파일 분리

`profile.json` 과 `config.json` 이 나뉘고 `.local` 오버라이드가 동작한다.

기존 `config.json` 의 `verify` 를 둘로 쪼갠다.
프로파일에 이름·순서·`scope`, config 에 `cmd`·`cwd`.

스킬에 `type`(`external` / `custom`)을 넣고 여섯 자리를 만든다.
마켓플레이스는 `GET /profiles` 와 정적 스킬 목록으로 흉내 낸다.

**팀이 나눠 쓸 수 있는지, 남의 것을 받아 쓸 수 있는지를 본다.**

### 5 · 레인과 토큰 집계

요청 여럿을 동시에 돌리고, 그게 얼마나 드는지 숫자로 본다.

```
awl run --lanes "키보드 조작" "인증 리프레시" "번들 축소"
awl lane new · awl lane rm
awl tokens <ticket>
```

격리하는 것(worktree · state · 포트)과 공유하는 것(설정 · 기록 · gotcha)을 나눈다.
기준 브랜치는 레인을 열 때 서 있던 브랜치이고 게이트 4 에서 거기로 되돌린다.

**병렬이 실제로 얼마나 드는지를 여기서 처음 안다.**

### 6 · 정리와 피드백

쌓인 것이 신호를 내고 도구 피드백이 자동으로 모인다.

제약에 `source` 와 `hits` 를 붙이고, `awl backlog` 로 정리 신호를 낸다.
3회 반복 승격 후보가 30건을 넘으면 부트스트랩 시 알림.

피드백은 기본 켜짐. LLM 이 정리한 최소 맥락만 보낸다.

**쌓인 것이 신호를 내는지, 도구가 스스로 개선 재료를 모으는지를 본다.**

### 개념 명령과 운영 명령

위 여섯 단계가 정한 건 **개념 명령**이다(`run` `doc` `tickets` `next` `stages` `record`
`review` `verify` `commit` `lane` `tokens` `backlog` `rules` `gotchas` `feedback`).

그 밖에 설계 문서가 이름을 정하지 않은 **운영 명령**이 있다. 도구를 설치·점검·정리하는
자리라 방법론과 층이 다르다 — 없으면 개념 명령을 쓸 수가 없다.

```
init · update · doctor · version-check   설치와 점검
status · brief · loop-summary · metrics  지금 상태와 지나온 것
remove                                    흔적 지우기
work                                      [레거시] 티켓 이전의 워크아이템
evolve · changelog · feedback-log         완료 뒤 정리
port                                      §14 의 포트 격리를 실행하는 자리
```

**설계에 이름이 없다는 것과 있으면 안 된다는 것은 다르다.** 다만 개념 명령과 겹치는
것(예: `work` ↔ 티켓)은 하나로 모은다 — 어휘가 둘이면 기록이 갈라진다.

## 18. 이 프로토타입에서 안 하는 것

```
인증           JWT · 토큰 버전 · 조직 판정
CI 연동        지금은 개인 PC 에서 직접 전송
개인 추적      조직 단위도 아직 없다
색인 DB        파일 grep 으로 충분한 동안은 안 만든다
정량 지표 형식  자유 서술 + 사용 횟수만
스킬 조합      자리당 하나
웹 UI          터미널로 충분한 동안은 안 만든다
```

**관찰 안 된 문제에 규칙을 만들면 엉뚱한 데를 조인다.**
좁게 시작해서 넓히는 쪽이 반대보다 안전하다.
