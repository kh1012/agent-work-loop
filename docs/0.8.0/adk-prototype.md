# ADK 프로토타입 — 기존 awl 에 개념을 얹는다

`adk-reference.md` 에 정리된 형식을 기존 awl 위에 얹어 실제로 돌려본다.

**이름이 둘이다.** `ADK` 는 방법론이고 `awl` 은 그것을 구현한 도구다.
패키지는 `agent-work-loop`, 명령은 `awl`.

> 초안엔 `@midasit-dev/awl` 로 적혀 있었다. 실제로는 0.1.x 부터 `agent-work-loop` 로
> 배포해 왔고, 지금 이름을 바꾸면 npm 에서는 별개 패키지가 되어 이미 설치한 사람들이
> 갱신을 못 받는다. 되돌리기 어려운 쪽을 피해 실제 이름으로 맞춘다(2단계 #10).

전부 한 번에 하지 않고 여섯 단계로 나눈다. **단계마다 실사용으로 검증하고 다음으로 간다.**

---

## 전제

**있다고 가정하는 것**

- 스킬 마켓플레이스는 있다. 지금은 정적 JSON 하나로 흉내 낸다
- 중앙 저장소는 `localhost:9999` 에 임시 서버로 띄운다. 디렉토리에 파일만 쓴다
- 인증은 나중에. 지금은 토큰 없이 받는다

**바꾸지 않는 것**

- awl 은 판단하지 않는다. 파일과 상태만 관리한다
- 로컬이 원본이고 원격은 사본이다. 원격이 죽어도 루프가 멈추면 안 된다
- 게이트는 산문이 아니라 도구 호출이다

**계약과 절차를 나눈다**

```
계약    무엇이 나와야 하는가        고정. .awl/stages.md
절차    어떤 순서로 어떻게 하는가    스킬. 프로파일이 지정하고 언젠가 비운다
```

**절차를 계약에 박으면 모델이 좋아졌을 때 못 뺀다.**
단단한 하네스일수록 크게 무너지므로 계약만 고정한다.

```
[gate 1] ─ 자유 ─ [gate 2] ─ 자유 ─ [gate 3] ─ 자유 ─ [gate 4]
```

게이트가 순서의 골격이고 그 사이는 자유다.
게이트에 도달할 때 계약이 만족되면 되고 거기까지 어떻게 갔는지는 안 따진다.

**작업 방식**

각 단계를 `/awl-loop` 으로 돌린다. 다만 **awl 자신을 고치는 티켓은 워크트리를 분리한다.**
돌고 있는 도구를 그 도구로 고치면 커밋이 섞인다. 이미 겪은 사고다.

## 단계 1 · 문서 구조

**목표**: 스펙 · 티켓 · 결정 · 용어집이 파일로 생긴다. 중앙은 아직 없다.

### 만들 것

```
~/.awl/
  config.json             전역 기본값. author · sync

<repo>/
  .awl/
    config.json           커밋
    profile.json          커밋
    config.local.json     untracked
    profile.local.json    untracked
    state.json            untracked
    records/               untracked
    ...
  docs/
    CONTEXT.md
    specs/20260725-143052-....md
    tickets/20260725-151203-....md
    decisions/20260725-160841-....md
```

**단계1 스냅샷 이후 후속 단계가 `.awl/` 아래에 더 추가했다** —
gitignore 허용목록(아래) 구조 자체가 이 확장을 이미 감당하므로 코드
결함은 아니다. 2026-07-28 기준 실제로 있는 파일: `skills-version.json`
(설치 시점 엔진 버전), `lane-meta.json`(레인 메타), `state.lock`
(state.json 동시쓰기 락), `verify-baseline.json`(검증 baseline),
`stages.md`, `tickets/<id>.json`(4게이트 티켓 모델), `records/`
(project-local 기록 디렉토리, `records-suffix.json`과 함께 — 레인/
동시 세션마다 파일명이 나뉜다), `home/`(레인 격리 gotchas/rules).
전부 untracked(위 허용목록엔 안 올라감) — 개인정보 유출 위험 없음.

**gitignore 는 허용목록으로 쓴다.** 새 파일이 생겨도 기본이 untracked 라
개인 메일이나 토큰이 딸려 올라가는 사고가 구조적으로 안 난다.

```gitignore
.awl/*
!.awl/config.json
!.awl/profile.json
```

`awl doc new spec|ticket|decision <제목>` 으로 뼈대를 만든다.

```
[YYYYMMDD]-[HHMMSS]-[kebab-제목].md
```

**순번을 안 쓴다.** 각자 브랜치에서 같은 번호를 잡아도 파일명이 달라
git 이 충돌을 안 내고 조용히 통과한다. Rails 가 순번에서 타임스탬프로 옮긴 것과 같은 이유다.

시각은 로컬로 쓰고 정확한 값은 프론트매터의 `created` 가 오프셋 포함 ISO 로 갖는다.
`id` 는 UUIDv7 을 발급한다. **참조는 UUID 라 파일명이 바뀌어도 링크가 안 깨진다.**

### 전역 설정

`awl init` 이 처음 실행될 때 `~/.awl/config.json` 이 없으면 만든다.

```json
{
  "author": "hong@midasit.com",
  "sync": {
    "records":  { "endpoint": "http://localhost:9999", "token": "" },
    "feedback": { "endpoint": "http://localhost:9999/feedback" }
  }
}
```

`author` 는 `git config user.email` 을 읽어 입력란을 미리 채우고
사람이 확인하거나 고쳐서 저장한다.

**git config 는 씨앗일 뿐이다.** 이후 런타임에는 config 만 읽는다.
git config 자체는 고치지 않는다.

**저장소마다 다시 묻지 않는다.** 전역에 있으므로 두 번째 저장소부터는 건너뛴다.
저장소가 덮으려면 `.awl/config.json` 이나 `config.local.json` 에 쓰면 된다.

없으면 기록에 `author` 가 안 붙는다. **막지는 않는다.**

### 엔진은 전역 하나

`~/.awl/engine/` 같은 사본을 두지 않는다. npm 패키지가 유일한 엔진이다.

```
업데이트    npm i -g <패키지>@latest
저장소      버전을 안 박는다. engineVersion 필드 없음
```

스키마가 바뀌면 관용적으로 읽는다. 모르는 키는 무시하고 없는 키는 기본값을 쓴다.

### 스펙 뼈대

```markdown
---
id: <UUIDv7>
revision: <생성 시 빈 값. 저장할 때 본문 sha256>
organization: <config 에서>
project: <config.repository 에서>
title:
status: draft
domain:
terms: []
verification: [binary]
tickets: []
decisions: []
created: <오늘>
updated: <오늘>
---

## Request
> (사용자가 던진 원문 그대로)

## Instruction

## Constraints

## Conditions

## Out of scope
```

### stages.md

`awl` 이 `.awl/stages.md` 를 생성하고 CLAUDE.md 가 참조한다.

```markdown
# CLAUDE.md
@.awl/stages.md
```

**계약만 넣는다.** 표 하나면 된다.

```markdown
| 단계 | 입력 | 출력 | 끝났다는 판정 |
|---|---|---|---|
| investigation | 조건 · 기존 finding | finding 목록 + file:line | 조건을 건드리는 경로가 전부 목록에 있는가 |
| clarification | 코드 · 계획 | 정한 것 목록 또는 "없음" | 코드로 답할 수 있는 질문이 안 남았는가 |
| implement | 조건 · finding | 커밋 | 검증이 통과하는가 |
```

untracked 라 항상 현재 버전이다. `awl doctor` 가 없거나 낡았으면 재생성한다.
참조가 안 되면 마커 사이를 갱신하는 방법으로 떨어뜨린다.

AGENTS.md 도 같은 파일을 가리킨다. 도구마다 읽는 파일이 다르기 때문이다.

### 검사기

`awl doc lint` 를 만든다. 다음을 잡는다.

- 조건이 EARS 다섯 문형(언제 / 만약 / 동안 / 어디서 / 항상)으로 시작하는가
- 조건에 질적 표현이 있는가 (적절한 · 깔끔한 · 최적화된 · 충분한)
- 스펙 본문에 파일 경로가 있는가 (있으면 안 된다. 경로는 finding 에만)
- 파일명이 `YYYYMMDD-HHMMSS-kebab` 형식인가
- 용어집의 `- 쓰지 않음:` 목록에 있는 단어가 문서에 쓰였는가

### 이 단계의 종료 판정

```
언제 awl doc new spec 을 실행하면, 프론트매터가 채워진 파일이 생성되어야 한다
언제 조건이 EARS 문형이 아니면, awl doc lint 가 실패해야 한다
언제 스펙 본문에 파일 경로가 있으면, awl doc lint 가 실패해야 한다
언제 파일명이 형식에 안 맞으면, awl doc lint 가 실패해야 한다
언제 git config user.email 이 있으면, init 이 그 값으로 입력란을 채워야 한다
언제 두 번째 저장소에서 init 을 실행하면, author 를 다시 묻지 않아야 한다
언제 전역 config 가 없으면, 기록에 author 가 안 붙되 진행은 되어야 한다
언제 .awl 에 새 파일을 만들면, gitignore 를 안 고쳐도 untracked 여야 한다
언제 awl 을 업데이트하면, stages.md 가 새 버전으로 재생성되어야 한다
```

## 단계 2 · 티켓과 게이트

**목표**: 스펙에서 티켓이 도출되고, 게이트 네 개가 실제로 멈춘다.

### 도출

`awl tickets derive <spec-id>` 를 만든다.
조건 하나에 티켓 하나가 기본. 여러 조건이 공유하는 기반은 `conditions: []` 인 별도 티켓.
의존이 곧 구현 순서다.

**도출은 기계적이지만 확정은 게이트를 거친다.**

### 게이트 네 개

기존 게이트 두 개를 네 개로 늘린다.

```
게이트 1  티켓 확정      요청 층    coverage 판정
게이트 2  착수          티켓 층
게이트 3  완료          티켓 층
게이트 4  요청 닫기      요청 층
```

`awl record gate` 에 `layer` 필드를 추가한다. `request` 또는 `ticket`.

### 접기

게이트 화면은 요약이 아니라 접기다.

```
펼침    실패 · 예상과 다른 것 · 범위 밖 · 리뷰 지적 · 정성 판정의 반대 의견
접힘    통과한 검증 · 예상대로 된 스파이크 · 충족된 조건 · 읽은 파일 목록
```

접힌 것은 `▸` 로 표시해 **거기 있다는 게 보이게** 한다.

### 이미 아는 것을 먼저 준다

`investigation` 이 시작할 때 같은 스펙의 다른 티켓 finding 을 재료로 넘긴다.

```
known   finding 6건 (ticket-1, ticket-2 에서)
        finding-2  tabindex 관리가 없다  LayersPanel.tsx:203  [확인 필요]

        위 finding 은 이미 확인됐다. 다시 찾지 않는다.
```

`[확인 필요]` 는 그 파일이 그 뒤 커밋에서 바뀌어 줄 번호가 밀렸을 수 있다는 뜻이다.

**리뷰어 재료 팩과 같은 규칙이다.** 세션이 시작할 때 이미 아는 것을 먼저 준다.

### 기본은 자가 검증

**서브에이전트를 안 띄운다.** 같은 세션이 만들고 같은 세션이 검증한다.

```
할 수 있다    조건 ↔ 검증 ↔ 커밋 대응 · 제약 위반 · 부존재 탐지
할 수 없다    이 구현이 적절한가 · 놓친 경우가 있는가
```

**부존재 탐지는 기계적이라 자가 검증에서도 성립한다.**

```
자기 커밋을 지우고 테스트가 통과하는지 본다
```

통과하면 그 테스트는 아무것도 안 재고 있다. 기본으로 켜둔다.

**안 본 것은 안 봤다고 남긴다.**

```
verification   typecheck · lint · test   통과
self-check     조건 대응 · 제약 · 부존재   통과
review         안 함                      [-]
```

`[-]` 는 실패가 아니라 안 한 것이다. 나중에 문제가 생겼을 때
그 구간이 교차 검증을 안 거쳤다는 것이 보여야 한다.

### --review 를 켰을 때

```
awl run --review "..."
```

리뷰어 세션 하나가 커밋을 순차로 본다. 스폰 1회, 대상은 커밋 단위.
기반 티켓은 즉시, 기능 티켓은 마지막에 모아서. 재리뷰는 고친 커밋만, 2회로 끊는다.

**재료를 싸서 주고 탐색을 막는다.**

```
$ awl review pack ticket-3
  조건 · 제약 · diff · 파일 목록 · finding · 검증 결과
```

```
아래 재료만으로 판단한다.
파일을 추가로 열지 않는다.
재료가 부족해 판단할 수 없으면 "재료 부족: <무엇>" 이라고 답한다.
```

### 얇은 오케스트레이션 스킬

`.claude/skills/awl/SKILL.md` 는 다섯 줄이면 된다.

```markdown
목표를 받으면 `awl next` 를 호출한다.
출력에 다음에 할 일과 그 방법이 있다. 그대로 따른다.
끝나면 `awl record` 로 결과를 넘기고 다시 `awl next` 를 부른다.
```

지시는 CLI 가 만든다. **프로파일만 바꿔도 동작이 바뀌고 스킬 파일은 안 건드린다.**

```
$ awl next
  ticket       ticket-4  접기·펼치기
  condition    condition-2  [전문]
  constraints  constraint-1, constraint-2  [전문]
  known        finding 6건  [전문]
  skill        (없음)

  게이트 2 에 도달하려면
    finding · clarification · verification

  게이트 3 에 도달하려면
    커밋 (검증 통과)
```

**단계를 하나씩 지시하지 않고 계약을 통째로 준다.**
게이트에 도달할 때 형식이 맞으면 되고 순서는 자유다.

`awl stages` 로 파이프라인 전체를 출력한다. `--short` 면 다섯 줄만.

### 모드

`--strict` `--auto` 를 스킬 호출에서 받는다. 아무것도 안 주면 `semi-auto` 다.
`state.json` 의 레인 단위 상태로 둔다. 세션 중 변경 가능하고 **변경도 기록에 남는다.**

```
strict      네 게이트에서 다 멈춘다
semi-auto   게이트 2·3 을 자동 승인한다        ← 기본
auto        전부 자동. 게이트 4 에서 펼친 요약만 낸다
```

**기본이 semi-auto 인 이유**는 시뮬레이션에서 strict 가 티켓 5개에 11회를 멈췄기 때문이다.
부담의 전부가 게이트 2·3인데 둘 다 기계 판정이 끝난 뒤에 묻는다.

### 이 단계의 종료 판정

```
언제 게이트 1 승인 기록이 없으면, phase 전환이 거부되어야 한다
언제 게이트 1 화면을 그리면, 범위 밖 항목이 접히지 않고 펼쳐져야 한다
언제 모드가 semi-auto 이면, 게이트 2·3 이 자동 승인되고 그 사실이 기록에 남아야 한다
언제 모드가 auto 이면, 게이트 4 가 완료 티켓·조건·검증·자동승인 횟수까지 펼쳐야 한다
언제 프로파일의 skills 를 바꾸면, SKILL.md 를 안 고쳐도 awl next 출력이 바뀌어야 한다
언제 skills 를 전부 비우면, 산출물이 계약을 여전히 만족하는지 비교할 수 있어야 한다
언제 아무 플래그도 안 주면, semi-auto 로 돌아야 한다
언제 기능 티켓이 끝나면, 리뷰 세션을 띄우지 않고 다음 티켓으로 넘어가야 한다
언제 기반 티켓이 끝나면, 그 자리에서 리뷰가 돌아야 한다
언제 같은 스펙의 다른 티켓에 finding 이 있으면, investigation 이 그것을 먼저 받아야 한다
언제 리뷰어에게 재료를 주면, 추가 파일 열기 없이 판단하거나 "재료 부족" 을 반환해야 한다
```

## 단계 3 · 중앙 저장소

**목표**: 스펙과 기록이 `localhost:9999` 에 쌓인다. 서버가 죽어도 루프는 돈다.

### 서버

**디렉토리에 파일만 쓴다.** DB 도 색인도 아직 없다.

```
POST   /records      → records/<owner>/<repo>/YYYY-MM.jsonl 에 append
POST   /specs        → docs/<owner>/<repo>/specs/<파일명> 에 write
GET    /specs        → 프론트매터만 모아 배열로
GET    /specs/:id    → 전문
GET    /specs?q=     → 본문 grep 수준으로 충분
GET    /profiles     → profiles/*.json 목록
GET    /profiles/:name → 프로파일 하나
POST   /feedback     → feedback/YYYY-MM.jsonl 에 append
```

`revision` 이 같으면 이미 받은 것으로 보고 무시한다.
기록은 `id` 로 중복을 거른다.

**봉투에 `author` 를 넣는다.**

```json
{
  "kind": "spec",
  "id": "...", "revision": "...",
  "organization": "...", "project": "...",
  "author": "hong@midasit.com",
  "frontmatter": { ... },
  "body": "..."
}
```

목적은 중앙에 물었을 때 이 영역을 아는 사람이 바로 나오는 것이다.
저장소로 넘어가 `git log` 를 보는 방식은 저장소를 가로지르는 집계가 안 된다.

`records` 는 필수, 문서는 생성자, `feedback` 은 안 넣는다.
**"가장 많이 안다"를 무엇으로 셀지는 아직 안 정했다.** 지금은 구분해 쌓아두기만 한다.

인증은 안 한다. 지금은 사내망 가정도 아니고 로컬이다.

### 전송

- 스펙은 **`closed` 가 될 때만** 보낸다
- 기록은 워크아이템이 끝날 때 보낸다
- 피드백은 발생할 때 보낸다

**로컬에 먼저 쓴다.** 원격은 그다음이다.

**큐가 아니라 커서다.** 기록은 이미 로컬 파일이므로 보낼 것을 따로 복사해 쌓지 않는다.
`state.json` 에 "여기까지 보냈다"를 두고, 보내면 앞으로 가고 실패하면 그 자리에 있는다.

```
endpoint 없음    전송 기능이 꺼진 상태
                 커서를 만들지 않는다. 재시도도 없다. 로컬에만 남는다
                 나중에 설정하면 그 시점부터 시작한다. 소급 전송 없음

endpoint 있음    실패하면 지수 백오프 1분 → 5분 → 30분 → 2시간 → 6시간 → 하루
                 7일 지나면 커서를 앞으로 밀고 로그만 남긴다
```

### doctor

```
sync
  endpoint   없음                     [-]
             전송이 꺼져 있습니다. 기록은 로컬에만 쌓입니다.

sync
  endpoint   http://localhost:9999    ok
  상태       재시도 중 (ECONNREFUSED)  [!]
             미전송 12건. 서버를 켜면 함께 나갑니다.
```

**꺼짐은 고장이 아니다.** 설정을 안 했을 뿐이고 기록은 로컬에 다 있다.

### 이 단계의 종료 판정

```
언제 서버가 꺼져 있으면, 루프가 멈추지 않고 기록이 로컬에 쌓여야 한다
언제 서버를 다시 켜면, 밀린 기록이 함께 전송되어야 한다
언제 endpoint 가 없으면, 재시도도 큐도 없이 로컬에만 쌓여야 한다
언제 endpoint 를 나중에 설정하면, 그 이전 기록은 소급 전송되지 않아야 한다
언제 같은 revision 을 두 번 보내면, 서버가 두 번째를 무시해야 한다
언제 스펙이 draft 나 active 이면, 중앙에 전송되지 않아야 한다
```

## 단계 4 · 프로파일 분리

**목표**: `profile.json` 과 `config.json` 이 나뉘고, `.local` 오버라이드가 동작한다.

### 파일 넷

```
.awl/profile.json          커밋       무엇을 · 어떤 순서로 · 어떤 정책으로
.awl/config.json           커밋       그걸 어떤 명령으로 · 어디로 보내나
.awl/profile.local.json    untracked  내 방식
.awl/config.local.json     untracked  내 머신
```

**`.local` 접미는 짝이 있는 override 에만 쓴다.**
짝이 없는 `state.json` 은 그냥 이름을 준다.

전역 → 저장소 → 개인 순으로 덮는다. `awl config --show-origin` 이 출처를 보여준다.

**검증은 config 에만 둔다.** 프로파일은 스킬만 담는다.

```json
// config.json
"verifications": [
  { "name": "typecheck", "cmd": "tsc --noEmit", "cwd": "packages/editor" },
  { "name": "test",      "cmd": "vitest run" },
  { "name": "a11y",      "cmd": "pnpm axe", "scope": "changed" },
  { "name": "e2e",       "cmd": "playwright test", "level": "request" }
]
```

```
scope: all | changed        changed 는 변경한 파일에서 나온 실패만
level: ticket | request     e2e 는 request
```

`{ "name": "typecheck" }` 만 담긴 목록은 공유 가치가 없다.
어떤 검사가 있는지는 자기 프로젝트를 보면 안다.
**프로파일이 담을 값어치가 있는 건 스킬이다.**

### 병합

```
base → local 순. local 이 이긴다
객체    키 단위로 깊게 병합
배열    name 키로 병합
비활성  skip: true
```

### 스킬

```json
{ "type": "external", "url": "…" }
{ "type": "custom",   "path": ".claude/skills/our-review" }
```

자리는 여섯. `spec` `investigation` `clarification` `spike` `implement` `review`.
`url` 만 필수, 나머지는 선택. **설치 목록을 따로 두지 않는다.**
`.claude/skills/<name>/` 이 있는지로 알고, 버전은 스킬이 커밋되므로 git 이 안다.
사본을 두면 어긋난다. `~/.awl/engine/` 과 같은 실수다.

마켓플레이스는 `GET /profiles` 와 정적 스킬 목록으로 흉내 낸다.

### 표시

**판정 기준과 만드는 방식을 구분해서 표시한다.**

```
verification
  e2e     [!] 로컬에서 건너뜀      경고
skills
  review  [i] 로컬 설정            정보
```

검증을 끄는 건 경고, 스킬을 바꾸는 건 정보다. **문제가 아니라 사실이기 때문이다.**

### 이 단계의 종료 판정

```
언제 profile.local 이 검증을 skip 하면, 게이트에 경고로 표시되고 기록에 남아야 한다
언제 profile.local 이 스킬을 바꾸면, 게이트에 정보로 표시되고 기록에 남아야 한다
언제 공유 프로파일을 받으면, config.json 이 덮어써지지 않아야 한다
언제 프로파일을 받으면, 거기 적힌 스킬 중 설치 안 된 것만 받아야 한다
```

## 단계 5 · 레인과 토큰 집계

**목표**: 요청 여럿을 동시에 돌리고, 그게 얼마나 드는지 숫자로 본다.

### 레인

**pipeline 은 loop 를 여러 개 돌리는 것이다.** 다른 물건이 아니다.

```
awl run "레이어 패널 키보드 조작"                          레인 하나
awl run --lanes "키보드 조작" "인증 리프레시" "번들 축소"    레인 셋
```

```
awl lane new keyboard auth bundle   worktree · 브랜치 · 포트만 만든다
                                    기준 브랜치를 레인 메타에 저장
사람이 터미널 셋을 열고 각각 /awl 을 돈다
awl lanes                           상황을 한눈에 본다
awl lane rm <name>                  미머지 커밋이 있으면 거부
```

**오케스트레이터 에이전트를 안 띄운다.** 세션당 레인 하나이고 터미널 관리는 사람의 몫이다.
레인마다 터미널이면 출력이 안 섞이고 사람은 어차피 하나씩 처리한다.

**격리하는 것과 공유하는 것을 나눈다.**

```
격리    worktree · state.json · 포트
공유    config · profile · 기록 · gotcha · finding
```

기록은 주 워킹카피의 `.awl/records/` 하나를 가리키고,
쓰기 경합은 파일명으로 없앤다.

```
.awl/records/2026-07.keyboard.jsonl
.awl/records/2026-07.auth.jsonl
```

읽을 땐 전부 훑는다. **정리 때 병합할 것이 없어진다.**

포트는 레인마다 오프셋을 주입하고, 못 나누는 검증은 직렬화한다.

```json
{ "name": "e2e", "exclusive": true }
```

### 기준 브랜치와 마무리

기준 브랜치는 main 이 아니라 **레인을 열 때 서 있던 브랜치**다.
보통 개인 기능 브랜치이고, 게이트 4 에서 거기로 되돌린다.

```
[Gate 4] 요청을 닫을 것인가

  마무리
    병합    awl/keyboard-nav  →  feature/editor-rework
    정리    기록 전송 · 워크트리 제거 · 브랜치 삭제

  (*) 병합하고 마무리   ( ) 판정만 하고 병합은 나중에   ( ) 보류
```

### 토큰 집계

**awl 은 토큰을 직접 못 센다.** 대신 시각을 갖고 있다.

```
awl 기록      ticket-3  시작 14:30:52  →  종료 14:47:11
세션 로그      그 구간 메시지들의 usage 합
```

```
$ awl tokens ticket-3
  총              82,400
    investigation  31,200   38%
    implement      28,900   35%
    review         13,200   16%
    verify          9,100   11%
```

`input / output / cache` 를 나눠 남긴다. 캐시 읽기는 싸서 합치면 실제 비용과 어긋난다.

**세션 로그를 읽는 부분은 한 파일로 몰아둔다.**
외부 형식에 의존하므로 바뀌면 거기만 고치면 되고 나중에 떼기도 쉽다.

### 이 단계의 종료 판정

```
언제 레인을 셋 열면, 서로 다른 worktree 와 포트에서 동시에 돌아야 한다
언제 awl lane new 를 실행하면, 에이전트를 띄우지 않고 준비만 해야 한다
언제 레인 A 가 gotcha 를 남기면, 레인 B 가 그것을 읽을 수 있어야 한다
언제 검증에 exclusive 가 붙으면, 레인이 여럿이어도 한 번에 하나만 돌아야 한다
언제 게이트 4 를 통과하면, 레인을 열 때 서 있던 브랜치로 병합을 제안해야 한다
언제 awl tokens 를 실행하면, 티켓별·단계별 사용량이 나와야 한다
```

## 단계 6 · 정리와 피드백

**목표**: 쌓인 것이 신호를 내고, 도구 피드백이 자동으로 모인다.

### source 와 hits

제약마다 두 필드를 붙인다.

```
source    어느 기록에서 왔나
hits      실제로 몇 번 걸렸나
```

검사기가 잡으면 자동으로 센다.
리뷰어가 잡는 경우, **지적할 때 어느 제약인지 반드시 지목하게 한다.**
해당하는 게 없으면 `없음` 이라고 명시한다. 그러면 새 제약 후보가 된다.

### 정리 신호

`awl backlog` 를 만든다.

```
[!] 3회 반복된 승격 후보가 31건 쌓였습니다.
    마지막 정리 2026-05-12

    clarification 반복   24건
    정량 지표 반복        7건

    함께 볼 것
      제약 hits 0        14건
      용어집 밖 용어      6건

    누구든 회의를 소집할 수 있습니다.
```

**세는 건 3회 이상 반복된 것뿐이다.** 나머지는 기록하되 신호에 안 넣는다.
누적이 아니라 **지난 정리 이후 증분**이다. 정리하면 리셋된다.

스킬 부트스트랩 시 표시한다.

### 피드백

```
자동    도구 오류 · 실패한 명령 · 예상 못 한 상태
        최소 맥락 (어떤 명령 · 어느 단계 · 상대 경로)
수동    awl feedback "…"
```

**로그를 통째로 던지지 않는다.** LLM 이 정리한 형태로 보낸다.
코드 내용 · 스펙 본문 · 토큰 · 절대 경로는 안 보낸다.

기본은 켜져 있다. 끄려면 `"feedback": false`.

### 이 단계의 종료 판정

```
언제 검사기가 제약 위반을 잡으면, 그 제약의 hits 가 증가해야 한다
언제 리뷰어가 제약을 지목하지 않으면, "없음" 을 명시해야 한다
언제 3회 반복 승격 후보가 30건을 넘으면, 부트스트랩 시 알림이 떠야 한다
언제 정리를 마치면, 증분 카운터가 리셋되어야 한다
언제 도구 오류가 발생하면, 코드 내용 없이 최소 맥락만 전송되어야 한다
```

## 하지 않을 것

**이 프로토타입에서 안 한다.** 필요해지면 그때 연다.

```
인증           JWT · 토큰 버전 · 조직 판정
CI 연동        지금은 개인 PC 에서 직접 전송
개인 추적      조직 단위도 아직 없다. 로컬만
색인 DB        파일 grep 으로 충분한 동안은 안 만든다
정량 지표 형식  자유 서술 + 사용 횟수만
스킬 조합      자리당 하나
웹 UI          터미널로 충분한 동안은 안 만든다
```

**관찰 안 된 문제에 규칙을 만들면 엉뚱한 데를 조인다.**
좁게 시작해서 넓히는 쪽이 반대보다 안전하다.

## 순서와 이유

```
1  문서 구조     나머지 전부가 여기 의존한다. 스펙이 없으면 티켓도 게이트도 없다
2  티켓과 게이트  절차가 실제로 멈추는지 여기서 판명된다
3  중앙          쌓인 것이 밖으로 나가는지. 서버가 죽어도 도는지
4  프로파일       팀이 나눠 쓸 수 있는지. 남의 것을 받아 쓸 수 있는지
5  레인과 토큰    병렬이 실제로 얼마나 드는지 숫자로 본다
6  정리와 피드백  쌓인 것이 신호를 내는지. 도구가 스스로 개선 재료를 모으는지
```

**단계마다 실사용으로 검증하고 넘어간다.** 다 만들고 한 번에 켜지 않는다.

각 단계가 끝나면 세션 기록을 코드 블록으로 남긴다.
무엇이 무너졌고 어떤 명령이 없어서 불편했는지가 다음 단계의 입력이다.
